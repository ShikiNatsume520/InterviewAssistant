# 前端重构阶段 9 设计草案：中断、恢复与集成收尾

> 实现状态：正式代码已完成，等待用户验收。

## 1. 本阶段定位

阶段 9 不增加新的 Agent 能力，而是让既有普通聊天、RAG、Resume、Research、知识库和模型配置在断线、刷新、切换会话与重复操作下形成可靠闭环。

本阶段会做：

- 明确“停止显示”“中断后端任务”“预期 Interrupt”三种不同状态；
- 切换会话前可靠中断当前运行任务；
- 重新进入 `interrupted` Thread 时自动从最近 checkpoint 恢复；
- 为发送、恢复和 Interrupt 决策增加操作 ID，防止重复执行；
- 改善冲突、断线和失败后的可操作反馈；
- 退役旧静态页面，补齐部署文档与安全检查清单；
- 完成关键用户故事回归和桌面浏览器验证。

本阶段不做：

- 不改变 LangGraph 的 checkpoint 粒度或图执行逻辑；
- 不把产品事件作为图输入或恢复依据；
- 不保证正在执行的节点从中间继续，仍按最近超级步 checkpoint 重跑；
- 不实现移动端适配、注册登录、跨设备同步或任务后台队列；
- 不引入 Docker、云平台或 CI 部署流水线，除非后续另行确定部署目标。

## 2. 三种“停下来”的语义

### 2.1 预期 Interrupt

计划确认、逐条审批、Resume standby、Research 入库确认属于图的正常等待：

- Thread 状态为 `waiting`；
- 不显示“异常中断”；
- 不自动执行 checkpoint；
- 用户提交决策后通过 `Command(resume=...)` 继续。

### 2.2 用户主动停止或切换会话

运行中的 Thread 被用户停止或离开时：

1. 前端请求后端取消该 Thread 当前任务；
2. 后端取消对应 SSE 执行任务；
3. `_run_locked_stream` 的 `finally` 释放 principal 级任务锁；
4. Thread 标为 `interrupted`，写入一次 `task.interrupted` 产品事件；
5. 前端确认状态已落定后再切换会话。

这意味着“停止”不是只停止浏览器渲染，而是真正终止当前运行；尚未完成的节点或超级步允许下次重跑。

### 2.3 页面关闭、刷新或网络断开

浏览器卸载阶段不适合依赖普通异步请求完成。因此：

- SSE 连接断开仍是主要取消信号；
- `pagehide` 只做 best-effort 通知，不承诺一定送达；
- 后端流生成器取消时必须在 `finally` 释放锁并标记 `interrupted`；
- 进程异常退出遗留的 `active_tasks` 继续由启动恢复逻辑清理。

## 3. 显式取消接口草案

```text
POST /v1/threads/{thread_id}/cancel

200 { status: "interrupted" }
200 { status: "waiting" | "idle" }  # 已经自然结束，幂等返回当前状态
404                              # 不存在或不属于当前身份
```

后端维护仅存在于当前进程内的 `task_id → asyncio.Task` 活动注册表。SQLite `active_tasks` 仍负责互斥和崩溃恢复，但不保存不可序列化的运行任务对象。

取消接口必须是幂等的。重复取消不得重复写 `task.interrupted`。

## 4. 会话切换交互

点击另一个会话、新建会话或进入知识库时：

- 当前 Thread 不在运行：立即切换；
- 当前 Thread 正在运行：侧栏显示“正在中断…”，暂时锁定重复导航；
- 后端确认取消后完成导航；
- 取消失败：留在当前页面，给出“重试中断”与“留在当前会话”，不悄悄切换。

直接修改地址、刷新或关闭标签页无法等待确认，按断线语义处理。

## 5. 自动恢复

进入 Thread 后，先拉取产品事件与 Thread 元数据：

- `waiting`：展示待审批卡片，不自动恢复；
- `idle`：正常展示；
- `running`：表示另一个标签页或尚未完成的请求正在运行，只观察，不再启动第二次执行；
- `interrupted`：如果当前身份已有模型配置，自动调用一次 `/v1/checkpoint`；游客缺少配置则先打开模型设置，保存后再恢复。

每次路由进入只允许触发一次自动恢复，避免状态刷新导致循环。恢复期间显示“正在从最近检查点恢复”。如果遇到 principal 级任务冲突，指出正在运行的会话，不自动重试风暴。

## 6. 操作幂等

前端对以下动作生成 UUID `operation_id`：

- 新消息发送；
- checkpoint 恢复；
- Interrupt 批准、拒绝、建议或入库决定。

后端以 `(principal_id, operation_id)` 建立唯一约束，记录 `running/completed/failed`。语义为：

- 首次收到：执行；
- 相同 ID 正在执行：返回稳定冲突，前端转为观察并刷新时间线；
- 相同 ID 已完成：不再执行图，前端刷新产品时间线获得结果；
- 网络失败后的用户重试复用原 operation ID；用户明确发起的新动作使用新 ID。

账本只保存操作标识、Thread、状态和时间，不保存 API Key、消息正文或图输入。产品事件仍可能因 checkpoint 重跑而出现语义重复，这是此前已经接受的行为；操作幂等只解决同一 HTTP 用户动作被重复提交。

### 6.1 Interrupt 身份隔离

`operation_id` 只能标识一次 HTTP 操作，不能标识业务审批点。每个逻辑 Interrupt 还必须拥有稳定且独属的 `interrupt_id`：

- 子图用会话、工具调用、阶段与该阶段稳定序号生成确定性 UUID；同一 checkpoint 重跑复用原 ID，不生成新的审批身份；
- `interrupt.requested` 产品事件携带 `phase + interrupt_id`；前端提交决定时原样回传二者；
- FastAPI 在执行 `Command(resume=...)` 前，将回传 ID 与当前 checkpoint 的 pending Interrupt 比对；不匹配返回 `INTERRUPT_ID_MISMATCH`；
- 图节点再次校验身份。深研的“研究计划确认”和“是否入库确认”属于两个独立恢复域，旧计划批准即使被 LangGraph resume scratchpad 重放，也只能触发入库确认重新挂起，不能进入导入节点；
- `interrupt.resolved` 只解除相同 ID 的 `interrupt.requested`，前端不能用阶段名或事件先后关系猜测对应关系。

因此，`operation_id` 解决请求重复提交，`interrupt_id` 解决审批决定串用；二者不可合并。

## 7. 错误与重试

- 在服务端尚未接受操作前失败：允许原操作 ID 重试；
- 服务端是否接受不确定：先刷新 Thread/时间线，再用相同操作 ID重试；
- 图内部失败：展示 `task.failed`，允许从 checkpoint 创建新的恢复操作；
- 409 任务冲突：展示活动 Thread，而不是笼统的“已有任务”；
- 认证失效：重新建立游客身份前明确提示会进入新的隔离空间，不能假装恢复旧数据。

## 8. 旧页面退役与部署边界

- `/` 只提供 `frontend/dist/index.html`；未构建时返回明确 503，不再回退 `static/index.html`；
- 保留 `/static` 仅限仍被正式产品引用的资源，确认无引用后再删除旧页面文件；
- README 改写为当前项目说明，包含 `uv` 安装、前端构建、FastAPI 启动、Studio 启动和生产反向代理说明；
- 生产检查至少包括 HTTPS、`IA_COOKIE_SECURE=true`、开发登录关闭、`.env` 不进入静态产物、数据目录权限与备份策略。

第一版支持当前主流桌面版 Chrome、Edge、Firefox；不承诺移动端布局。

## 9. 快速原型

原型 `prototypes/phase9_cancel_idempotency_probe.py` 验证：

1. 取消 asyncio 执行任务会进入 `finally`，Thread 标为 `interrupted` 并释放 principal 锁；
2. 释放后同一 principal 能立即在另一个 Thread 获取任务锁；
3. 相同 principal 的相同 operation ID 只会首次进入执行；
4. 不同 principal 可以使用相同 operation ID，不会互相影响。
