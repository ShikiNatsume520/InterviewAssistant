# 未来优化

本文记录不属于当前重构阶段正式范围、但已经形成初步方向的后续架构优化。具体实施前仍需重新进行边界陈述、快速原型和方案评审。

## 1. 分层知识库与统一检索编排

### 1.1 问题背景

随着系统能力扩展，可检索数据会逐渐包含：

- 系统公共技术知识；
- 用户个人知识；
- 用户上传的简历；
- 用户长期记忆；
- 深度研究成果；
- Thread 会话历史。

如果把这些数据直接放进同一个无分区检索空间，会产生明显的跨域污染。例如搜索简历中的项目名称时返回技术教程，或者回答技术概念时混入用户简历片段。

因此需要明确：

> 所有搜索可以统一由 RAG Agent编排，但不同数据不应无区分地共享同一存储、索引或结果池。

```text
统一检索编排
    ≠ 统一存储
    ≠ 统一索引
    ≠ 统一候选结果池
```

### 1.2 目标架构

```text
调用 Agent
    │
    ▼
Retrieval Router / RAG Agent
    ├─ Knowledge Retriever
    ├─ Resume Retriever
    ├─ Research Retriever
    ├─ Memory Retriever
    └─ Conversation Retriever
            │
            ▼
    各数据域适合的存储与索引
```

RAG Agent负责：

- 判断查询属于哪个数据域；
- 注入当前用户的强制访问范围；
- 选择关键词、语义、混合或元数据检索；
- 必要时并行检索多个数据域；
- 对候选结果去重、重排和置信度判断；
- 将不同数据域的证据分别组织后交给调用 Agent。

### 1.3 四个核心分层维度

#### 数据域 `corpus`

表示被检索的数据类型：

```text
knowledge       系统公共知识与个人知识
resume          用户简历
research        深度研究产物
memory          用户长期记忆
conversation    Thread 会话历史
```

默认一次查询只进入一个数据域，避免不同类型的数据相互污染。

#### 所有权 `owner`

表示访问边界：

```text
public                  系统公共资料
principal:{user_id}     某个游客的个人资料
developer               开发人员作用域
```

`owner_id` 必须由后端根据已经认证的 Session 注入，禁止由 LLM 或客户端任意指定。

#### 检索方式 `retrieval_mode`

```text
keyword
semantic
hybrid
metadata
graph
```

- 简历中的项目名、技能和文件名优先使用关键词或元数据检索；
- 技术概念问答使用语义或混合检索；
- 用户长期记忆按 namespace 和结构化字段查询；
- 图检索只在未来出现明确跨文档关系推理需求时考虑。

#### 业务范围 `scope`

```text
resume_id
thread_id
document_ids
tags
created_after
source_type
```

业务范围在数据域和用户权限之上进一步缩小实际候选集合。

### 1.4 各数据域的建议存储

#### 技术知识

```text
源数据：Markdown
索引：index.md + 向量索引
检索：keyword / semantic / hybrid
引用：文件名 + start_line / end_line
```

#### 用户个人知识

```text
源数据：用户上传 Markdown、确认入库的深研报告
索引：用户级关键词索引 + 向量分区
权限：public OR owner_id=current_principal
```

公共知识只读，个人知识只允许所属用户管理。

#### 简历

```text
源数据：SQLite ResumeDocument
索引：SQLite FTS 或受控关键词扫描
检索：keyword / metadata
过滤：principal_id + resume_id
```

简历不进入知识向量库，也不与技术知识共享候选结果池。

#### 用户长期记忆

```text
源数据：LangGraph Store
检索：namespace + principal_id
用途：个性化上下文
```

长期记忆不作为普通知识引用，也不进入公共知识检索。

#### Thread 会话历史

```text
源数据：LangGraph checkpoint + 产品事件时间线
范围：当前 Thread
用途：执行恢复、对话连续和前端展示
```

会话历史不进入公共 RAG，未来如需历史搜索，应使用独立的 Conversation Retriever。

### 1.5 统一检索请求草案

底层可以采用统一协议：

```python
class RetrievalRequest:
    query: str
    corpus: Literal[
        "knowledge",
        "resume",
        "research",
        "memory",
        "conversation",
    ]
    search_type: Literal[
        "keyword",
        "semantic",
        "hybrid",
        "metadata",
    ]
    resume_id: str | None
    document_ids: list[str]
```

协议中不提供可由模型填写的 `owner_id`。后端执行时生成有效作用域：

```text
effective_scope
├─ authenticated_principal_id
├─ permitted_visibility
├─ requested_corpus
└─ requested_resource_scope
```

### 1.6 面向 Agent的工具不必完全统一

底层使用统一 Retriever Registry，不代表必须向 Main Agent暴露一个参数复杂的万能工具。

推荐继续提供业务语义明确的小工具：

```text
list_resumes
search_resumes
rag_agent
```

它们内部可以复用统一的：

- 查询规范化；
- 用户作用域注入；
- 关键词检索实现；
- 结果去重与排序；
- 行号和来源元数据；
- 日志脱敏和权限审计。

这样既保留统一检索架构，也降低 LLM 选错 `corpus`、过滤器或资源 ID 的概率。

### 1.7 跨域检索规则

默认只检索一个数据域。只有业务场景明确要求时才执行跨域检索。

例如：

> 根据知识库中的简历写作规范，检查我的后端简历。

执行方式：

```text
并行检索
├─ knowledge：检索简历写作规范
└─ resume：读取或搜索指定简历
        ↓
分别组织结果
├─ knowledge_evidence
└─ resume_evidence
        ↓
交给 Resume Agent
```

不同数据域的结果不能先混成一个无来源 Top-K，否则相似度分数不可直接比较，权限和引用语义也会变得模糊。

### 1.8 建议的检索流水线

```text
1. 识别查询意图
2. 选择数据域
3. 注入用户权限与资源范围
4. 规范化或改写查询
5. 选择检索器
6. 在各数据域独立召回候选
7. 去重与重排
8. 判断置信度和知识缺口
9. 组织带来源的 Evidence Pack
10. 交给调用 Agent生成回答或继续操作
```

### 1.9 向量 collection 策略

不建议：

- 每个文档一个 collection；
- 每个 Thread 一个 collection；
- 所有数据类型共用一个没有强制过滤的 collection。

建议根据 embedding、数据 schema 和查询模式划分 collection，并通过 metadata/payload 强制过滤用户作用域。

```text
knowledge_vectors
├─ visibility=public
└─ visibility=personal, owner_id=...
```

简历继续使用 SQLite/FTS，不创建向量 collection。

在用户规模较小时，可以选择更直观的物理隔离；用户规模增大后，可评估共享 collection + 强制 owner filter。迁移前必须通过隔离、性能和删除一致性原型验证。

### 1.10 GraphRAG 的适用边界

当前“知识与简历相互污染”的问题通过数据域路由、权限过滤和独立 Retriever 即可解决，不需要引入 GraphRAG。

只有出现以下需求时才考虑图检索：

- 需要跨大量文档连接实体与关系；
- 需要回答整个资料集合的全局性问题；
- 普通向量 Top-K 难以完成多跳关联推理；
- 已经具备稳定的实体、关系和事实抽取质量。

GraphRAG 属于未来独立技术阶段，不应成为当前知识库隔离的前置条件。

### 1.11 对当前项目的演进路径

#### 第一步：保持显式业务工具

```text
知识：rag_agent
简历：list_resumes + search_resumes
```

先完成权限隔离和正确的产品闭环。

#### 第二步：抽取 Retriever Registry

统一注册不同数据域的 Retriever，但不改变 Agent对外工具语义。

```text
Retriever Registry
├─ knowledge.keyword
├─ knowledge.semantic
├─ resume.keyword
├─ memory.namespace
└─ conversation.thread
```

#### 第三步：加入混合检索与重排

在知识域内组合关键词和向量召回，再执行统一重排和置信度判断。简历仍保持关键词优先。

#### 第四步：按真实需求增加跨域编排

只为明确用户故事增加跨域查询模板，不允许模型任意全域搜索。

#### 第五步：评估图检索

当技术知识和深研资料规模、关系复杂度达到普通 RAG 的瓶颈后，再通过原型评估 GraphRAG。

### 1.12 验收原则

- 搜索简历时不会返回知识文章；
- 搜索技术知识时不会返回用户简历；
- 用户无法通过查询参数访问其他用户资源；
- 公共知识和个人知识能够明确区分来源；
- 跨域搜索必须由业务场景显式触发；
- 每条结果保留 corpus、资源 ID、文件名和行区间；
- Retriever 或产品事件失败不能改变 LangGraph checkpoint 的执行真相；
- 删除资源时同步清理对应索引，不影响其他数据域或用户。
