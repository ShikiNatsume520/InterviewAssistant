# 前端重构阶段 7 设计草案：个人知识库管理与隔离

## 1. 阶段目标

本阶段建立一条完整且可验证的个人知识生命周期：

1. 当前游客上传 Markdown，或批准保存深研报告；
2. 后端登记资源并调用 Index Agent 建立关键词索引与向量索引；
3. 知识库页面展示资源、来源和索引状态；
4. RAG 只能联合检索公共知识与当前游客的个人知识；
5. 删除或重新索引只影响当前游客的资源；
6. 所有引用继续保留文件和行区间，并能区分公共/个人来源。

本阶段不实现注册登录、跨设备同步、Skill 管理、PDF/DOCX 导入和知识正文在线编辑。

## 2. 当前实现的关键缺口

- 公共 Markdown、`index.md` 和 Chroma collection 都是全局单例。
- Index Agent 只接受全局 `data/markdown` 下的文件名，没有资源归属概念。
- RAG 的关键词和语义检索都不知道当前 `principal_id`。
- 知识文件没有资源元数据表，无法可靠展示状态、来源、失败原因和执行删除。
- 深研批准后仅在 Research 状态中记录 `import_status=pending`，尚未真正导入。
- 仅依赖文件名作为引用身份，同名公共/个人文件可能冲突。

## 3. 隔离方案

### 3.1 全局多租户持久化边界

公共预备知识和静态资源是当前系统中唯一允许所有用户共同读取的业务内容。其他数据即使为了运维和迁移便利而共用底层 SQLite 文件，也不代表业务上共享：

| 持久化内容 | 第一版物理存储 | 强制隔离键 | 是否允许跨用户读取 |
|---|---|---|---|
| LangGraph checkpoint | 共享 `checkpoints.sqlite` | `thread_id`，且 Thread 必须先通过 principal 归属校验 | 否 |
| 长期记忆 Store | 共享 `store.sqlite` | 服务端注入 `("memory", principal_id, ...)` namespace | 否 |
| Session、Thread、事件、简历、知识元数据 | 共享 `app.sqlite` | 表内 `principal_id` + Repository 归属校验 | 否 |
| 公共 Markdown、关键词索引、向量索引 | 公共目录与公共 collection | `scope=public` | 是，只读 |
| 个人 Markdown、关键词索引、向量索引 | 每 principal 独立目录与 collection | 认证 Session 对应的 `principal_id` | 否 |

第一版继续让 checkpoint、Store 和业务表共用各自的数据库文件，不为每个游客创建三套 SQLite。原因是当前主图在应用启动时绑定一个 checkpointer，按用户动态切换数据库会显著增加图编译、连接管理、Studio 调试、迁移和备份复杂度。当前安全边界必须由服务端统一保证：

1. HTTP 请求只能从 HttpOnly Session Cookie 获得 principal；
2. 前端、LLM 工具参数和请求体中的任意用户 ID 都不可信；
3. 访问 checkpoint 前必须先执行 `require_thread(principal, thread_id)`；
4. Store namespace 只能由服务端用可信 principal 构造；
5. Repository 查询、修改和删除都必须同时包含资源 ID 与 principal 边界；
6. LangGraph Studio 属于本地开发管理能力，不作为面向普通用户的接口暴露。

未来若部署为不可信的正式多租户服务，再评估 PostgreSQL、数据库行级安全策略或每用户 checkpoint 数据库。本阶段不提前引入这些基础设施，但测试必须覆盖“知道其他用户资源 ID 或 thread_id 也不能越权”。

### 3.2 知识库的物理隔离

采用“公共库 + 每个 principal 独立个人库”的物理隔离：

```text
公共库（兼容现有数据）
├── data/markdown/*.md
├── data/index.md
└── data/chroma/ 中的 knowledge_base collection

个人库
└── data/knowledge/principals/<principal_id>/
    ├── documents/<resource_id>.md
    └── index.md

个人向量
└── data/chroma/ 中每个 principal 的独立 collection
```

第一版保留已经投入使用的公共知识路径，避免为阶段 7 搬移和重新向量化全部公共资料；新增个人知识才进入 `data/knowledge/principals/`。这不改变公共/个人的隔离语义。

Chroma 使用一个公共 collection 和每个 principal 一个个人 collection。collection 名由安全的稳定散列生成，不直接拼接用户输入。

选择独立 collection 的原因：

- 查询和删除默认具备物理边界，不依赖每个调用点都正确附加 owner filter；
- 同一资源 ID 或文件名不会跨用户覆盖；
- 将来删除游客数据、迁移用户或隔离 Skill 时边界更清楚；
- 公共与个人检索可以分别召回，再在 RAG 层统一排序、去重和判断知识缺口。

## 4. 资源模型

SQLite 新增知识资源表，文件系统和 Chroma 不承担业务元数据职责。

```text
KnowledgeResource
  id                  稳定 UUID
  principal_id        个人资源所有者；公共资源使用独立公共作用域
  scope               public | personal
  source_type         upload | research
  display_name        用户可见名称
  storage_name        <resource_id>.md，不接受用户路径
  status              pending | indexing | ready | failed | deleting
  failure_reason      最近一次失败摘要
  created_at
  updated_at
```

Markdown 正文不写入 SQLite。上传文件名只作为 `display_name`；真实落盘名固定使用 `resource_id.md`，避免路径穿越、同名覆盖和重命名引发索引失效。

向量 metadata 至少增加：

```text
resource_id, scope, owner_id, display_name,
start_line, end_line, heading
```

产品引用以 `resource_id + 行区间` 为稳定身份，`display_name` 只负责展示。

## 5. 正式导入服务与 Index Agent

新增非对话的知识库服务，统一提供：

- `import_markdown(principal, display_name, content, source_type)`；
- `reindex_resource(principal, resource_id)`；
- `delete_resource(principal, resource_id)`；
- `list_resources(principal)` / `read_resource(principal, resource_id)`。

服务负责归属校验、原子落盘、状态流转和唤醒 Index Agent。Index Agent 仍是后台图，但输入改为显式作用域：

```json
{
  "scope": "personal",
  "principal_id": "guest-id",
  "resource_ids": ["resource-id"]
}
```

Index Agent 根据作用域解析目录、`index.md` 和 collection；调用者不能传任意路径。删除必须同时清理资源文件、该作用域 `index.md` 中的引用以及 collection 中匹配 `resource_id` 的向量。

同一作用域内的导入、重建和删除必须串行执行。原因是 Index Agent 会读取完整 `index.md` 后再覆盖写回；如果两个请求并发执行，后写入者可能覆盖先写入者的索引更新。第一版单进程服务采用“公共作用域一把锁 + 每个 principal 一把锁”，锁覆盖文件、`index.md` 和 Chroma 更新的完整临界区；不同 principal 仍可并行。若未来部署多个后端进程，必须把它升级为数据库租约或外部任务队列，不能继续依赖进程内锁。

第一版建议导入/重建接口等待本次 Index Agent 完成后返回，资源状态仍持久化为 `pending → indexing → ready/failed`。这样不引入不可恢复的进程内后台任务；前端在请求期间显示“正在索引”，失败后允许重试。若实测索引耗时不可接受，再单独讨论持久化任务队列，不在本阶段提前扩展。

## 6. 深研批准后的数据流

Research wrapper 调用子图时必须把 `principal_id` 作为子图输入。知识确认后的分支为：

```text
knowledge_confirm
  ├─ reject  → END（不保存正文）
  └─ approve → import_knowledge → END
```

`import_knowledge` 只调用正式知识库服务，不直接写文件、Chroma 或调用 Index 子图内部节点。服务成功后写入：

```text
import_status = completed
knowledge_resource_id = <resource_id>
```

失败时写入 `import_status=failed` 和精简错误信息，完整报告仍只留在该次 checkpoint，不自动成为可检索知识。wrapper 的最终 ToolMessage 继续只携带精简元数据，并明确是否入库成功。

导入必须抵抗 LangGraph 超级步重跑。Research wrapper 将稳定的 `tool_call_id` 传入子图，导入服务使用类似 `research:<thread_id>:<tool_call_id>` 的幂等键，并在资源表建立 `UNIQUE(principal_id, idempotency_key)`：

- 首次调用创建资源并索引；
- 索引失败后重跑复用同一 `resource_id` 并继续索引；
- 已成功后重跑直接返回原资源；
- 同一幂等键在不同 principal 下互不影响。

## 7. RAG 联合检索

Main Agent 调用 RAG wrapper 时，由 wrapper 从可信 `config.configurable.user_id` 获取当前 principal；LLM 工具参数中不暴露、也不接受用户 ID。

关键词检索：分别读取公共和当前个人 `index.md`，在各自目录内 grep，再合并排序。

语义检索：分别查询公共 collection 和当前个人 collection，各取候选后合并排序。不得查询其他 principal collection。

返回 Citation 时增加 `resource_id`、`scope`、`display_name`，但仍保留 `file_path/start_line/end_line` 以兼容现有提示词和行级引用解析。

## 8. API 草案

```text
GET    /v1/knowledge/resources
POST   /v1/knowledge/resources             上传 Markdown 并索引
GET    /v1/knowledge/resources/{id}        读取当前用户资源
DELETE /v1/knowledge/resources/{id}        删除文件、关键词索引和向量
POST   /v1/knowledge/resources/{id}/reindex
```

公共资源随列表返回。对游客标记 `readOnly=true`；开发人员可以上传、重新索引和删除公共知识。公共写操作必须由后端从认证 Session 判断 `principal.kind == developer`，不能相信前端提交的角色字段。

公共资源删除会影响所有用户的后续 RAG，因此使用区别于个人删除的确认文案，并同步清理公共 Markdown、公共 `index.md` 引用和公共 collection 向量。系统随代码预置但尚未登记为可管理资源的历史公共 Markdown，第一版是否允许直接删除，需要在正式实现前确认。

上传限制：仅 `.md`、UTF-8 文本、非空，并设置合理大小上限。所有接口从 HttpOnly Session Cookie 确定 principal，不接受前端提交 `principal_id`。

## 9. 前端交互草案

左侧导航新增“知识库”，路由 `/knowledge`。聊天会话侧栏保持固定，知识库页面替换中间/右侧内容区，不与聊天时间线混排。

页面结构：

- 顶部：标题、公共/个人数量、上传 Markdown 按钮；
- 筛选：全部、个人、公共、深研资料、索引失败；
- 资源列表：名称、来源、作用域、创建时间、索引状态；
- 个人资源操作：删除、重新索引；
- 公共资源：只允许查看；
- 拖拽 Markdown 到页面即可上传；
- 上传和重建期间禁用重复操作；失败项展示精简原因和“重新索引”。

删除不可撤销，必须二次确认。删除完成后该资料立即从列表和后续 RAG 结果中消失。

## 10. 快速原型与正式验收

快速原型验证：

- 共享 checkpoint 数据库中，必须先通过 Thread 所属 principal 才能取得 checkpoint；
- 共享 Store 中，长期记忆 namespace 只能返回当前 principal 的事实；
- 即使请求伪造其他 `principal_id`，服务端也只使用认证 Session 的 principal；
- 两个 principal 上传同名 Markdown 不冲突；
- A 的列表、读取和删除不能访问 B；
- A 的联合检索只返回公共资料和 A 的个人资料；
- 删除 A 的资料不会影响公共库或 B；
- 用户文件名不能决定落盘路径。

正式实现还需验证：

- 上传、深研批准、重建、删除四条完整链路；
- Index Agent 每次只操作显式作用域；
- RAG 两条管道都不存在跨游客召回；
- 行级引用及前端引用展示保持正确；
- ruff、mypy `--strict`、后端单元测试和前端构建通过。

## 11. 开始正式实现前需要确认

1. 第一版导入与重新索引采用“请求等待索引完成”，暂不引入后台任务队列。
2. 知识库页面可以查看 Markdown 正文，但不提供在线编辑。
3. 公共知识对游客只读；开发人员可上传、重新索引和删除。
4. 删除个人知识时二次确认，且不可撤销。
