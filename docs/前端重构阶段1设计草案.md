# 前端重构阶段 1：身份模式与多 Thread 设计草案

> 状态：快速原型通过，等待协商与正式实现批准
>
> 本文只设计阶段 1，不提前实现产品事件、知识库、Skill、React 正式页面或运行时 API Key 注入。

## 1. 阶段边界

### 本阶段实现

- 游客身份创建与恢复。
- 受控开发人员登录。
- 游客与开发人员数据作用域隔离。
- Thread 创建、列表、读取、重命名和删除。
- Thread 所有权校验。
- 同一 principal 的单活动任务锁基础。
- Thread 删除时清理对应 LangGraph checkpoint。

### 本阶段不实现

- 产品事件表和新 SSE 协议。
- React 正式工程和会话侧栏。
- Main/Resume 结构化交接。
- Research 进度事件。
- 个人知识库和 Chroma 隔离。
- 游客 API Key 运行时注入。
- Skill 安装与 Skill 表。

## 2. 快速原型

原型：[frontend_phase1_identity_thread_probe.py](../prototypes/frontend_phase1_identity_thread_probe.py)

已验证：

- 高熵 session token 可以恢复 principal。
- SQLite 只保存 token 哈希，不保存明文 session。
- 开发模式关闭时无法登录开发人员。
- 开发凭证错误时无法登录。
- 多次开发登录复用同一个稳定开发 principal，但签发不同 session。
- Thread owner 只取后端 principal，不接受客户端 owner 字段。
- 跨 principal 的列表、读取、重命名和删除均被拒绝。
- 游客和开发人员 Thread 作用域隔离。
- 一个 principal 同时只能获取一个活动任务锁。
- 当前 `AsyncSqliteSaver` 提供 `adelete_thread(thread_id)`。

## 3. 身份模型

统一把游客和开发人员称为 `principal`：

```text
Principal
├─ guest       游客作用域
└─ developer   本地开发作用域
```

### 3.1 游客

- 首次访问由后端创建随机 principal ID 和高熵 session token。
- 游客没有用户名、密码或个人资料。
- 同一 session 可以恢复其 Thread。
- session 丢失后无法证明自己是原 principal；第一版不提供找回能力。

### 3.2 开发人员

- 服务端必须设置显式开发模式开关。
- 开发登录还需要验证服务端配置的开发访问凭证。
- 所有开发登录复用固定 principal，例如 `developer-local`。
- 登录成功后签发普通 session，后续请求不重复携带开发访问凭证。
- 开发 principal 的 Thread 与游客完全隔离。
- LangGraph Studio 不经过该登录接口，继续直接使用 `.env`。

### 3.3 不信任客户端身份字段

请求体不允许提交以下字段决定归属：

```text
principal_id
owner_id
user_id
identity_kind
is_developer
```

后端必须先从 session 解析 `PrincipalContext`，再把 `principal.id` 用于查询和写入。

## 4. Session 传输建议

### 4.1 推荐：HttpOnly Cookie

身份 session 建议使用服务端设置的 Cookie：

```text
Name: ia_session
HttpOnly: true
Secure: 生产 true
SameSite: Strict
Path: /v1
```

它与 API Key Cookie 有本质区别：

- `ia_session` 只是随机身份凭证，不包含模型 API Key。
- React 不需要读取 session，浏览器自动随同源 `/v1` 请求发送。
- `HttpOnly` 可以降低 XSS 直接读取身份凭证的风险。
- API Key 仍由游客在需要模型运行的请求头中临时提交，不能放入 Cookie。

首版建议前端和 API 同源部署，以便使用 `SameSite=Strict`。如果未来跨域部署，需要重新设计 Cookie 和 CSRF 防护，不在本阶段处理。

### 4.2 数据库存储

数据库只保存：

```text
SHA-256(session_token)
```

session token 使用至少 256 bit 随机数。正式实现时可以增加服务端 pepper，但不是替代高熵随机 token。

### 4.3 Session 生命周期

建议游客 session 为持久 Cookie，使关闭浏览器后仍能恢复历史 Thread。第一版暂定有效期 30 天，每次成功访问是否滚动续期需要用户确认。

开发人员 session 可以使用较短有效期，例如 12 小时；重新登录不会丢失开发 principal 下的 Thread。

## 5. 开发人员模式

建议环境配置：

```text
IA_DEV_MODE=false
IA_DEV_ACCESS_TOKEN=<高熵开发访问凭证>
```

规则：

1. `IA_DEV_MODE` 不是 true 时，开发登录接口返回 404，不暴露该能力。
2. 启用时仍需校验 `IA_DEV_ACCESS_TOKEN`。
3. 比较凭证使用 constant-time compare。
4. 登录成功后签发开发 session Cookie。
5. 浏览器永远拿不到 `.env` 中的模型 API Key。
6. 后续模型配置阶段根据 `principal.kind=developer` 选择 `.env`。
7. 游客缺少 API Key 时不能回退到 `.env`。

### 待确认的开发登录体验

建议采用：开发人员在本地登录页填写一次 `IA_DEV_ACCESS_TOKEN`，成功后 12 小时内不再填写，也无需填写模型 API Key。

不建议只根据“请求来自 localhost”提供一键免密登录，因为反向代理、容器和端口转发会让来源判断不可靠。

## 6. 数据表草案

### `principals`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 随机 UUID；本地开发可使用稳定保留 ID |
| `kind` | TEXT | `guest` / `developer` |
| `created_at` | TEXT | UTC 时间 |

### `sessions`

| 字段 | 类型 | 说明 |
|---|---|---|
| `token_hash` | TEXT PK | session token 哈希 |
| `principal_id` | TEXT FK | 所属 principal |
| `created_at` | TEXT | 签发时间 |
| `expires_at` | TEXT | 过期时间 |
| `last_seen_at` | TEXT | 可选，用于续期与清理 |

### `threads`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | 同时作为 LangGraph `thread_id` |
| `principal_id` | TEXT FK | 资源 owner |
| `title` | TEXT | 会话标题 |
| `status` | TEXT | 本阶段至少 `idle` / `running` / `interrupted` |
| `created_at` | TEXT | 创建时间 |
| `updated_at` | TEXT | 排序时间 |

### `active_tasks`

| 字段 | 类型 | 说明 |
|---|---|---|
| `principal_id` | TEXT PK | 保证每个 principal 只有一行 |
| `thread_id` | TEXT FK | 当前运行 Thread |
| `task_id` | TEXT | 当前运行标识 |
| `started_at` | TEXT | 启动时间 |

本阶段不创建 `events`、`knowledge_bases` 或 `skills` 表。

## 7. API 草案

### `POST /v1/identity/guest`

首次进入时创建游客 principal 和 session Cookie。如果已有有效 session，幂等返回当前身份，不重复创建。

响应：

```json
{
  "kind": "guest",
  "developerModeAvailable": false
}
```

### `GET /v1/identity`

读取当前 session：

```json
{
  "kind": "guest",
  "developerModeAvailable": true
}
```

不返回 principal ID 的必要性较低；如果前端不需要，应避免暴露。

### `POST /v1/identity/developer`

请求：

```json
{
  "accessToken": "开发访问凭证"
}
```

成功后覆盖当前 `ia_session` Cookie，进入稳定开发 principal。开发模式关闭时返回 404，凭证错误返回统一 401。

### `POST /v1/identity/guest/reset`

离开开发人员模式或主动创建全新游客身份。该操作会签发新游客 session，不删除旧 principal 数据。

### `POST /v1/threads`

```json
{
  "title": "新会话"
}
```

后端从 session 写入 owner。

### `GET /v1/threads`

只返回当前 principal 的 Thread，按 `updated_at DESC` 排序。

### `GET /v1/threads/{thread_id}`

返回 Thread 元数据与现有 checkpoint 状态摘要。本阶段不返回产品事件。

### `PATCH /v1/threads/{thread_id}`

```json
{
  "title": "新的标题"
}
```

### `DELETE /v1/threads/{thread_id}`

建议顺序：

1. 校验 owner。
2. 在应用数据库内原子确认该 Thread 没有活动任务，并删除 Thread 元数据。
3. 调用 `checkpointer.adelete_thread(thread_id)` 清理 checkpoint。

删除操作需要幂等。若 checkpoint 已不存在，再次请求仍可完成元数据删除。

## 8. 与现有后端的连接

- 现有 `_state["current_thread_id"]` 将被移除。
- 现有 `/v1/thread` 将由新的 `/v1/threads` API 取代。
- 现有 `/v1/chat`、`/v1/checkpoint` 和 `/v1/state` 在本阶段只增加 session 与 Thread owner 校验，不改业务协议。
- LangGraph config 继续使用：

```python
{"configurable": {"thread_id": thread.id}}
```

- 现有 `user_id="default"` 不能继续作为长期记忆 owner；本阶段需要明确改为 principal ID，还是暂时禁用新身份下的长期记忆。这一点需要协商。

## 9. 测试草案

- 首次游客创建与已有 session 幂等恢复。
- 伪造、过期和不存在的 session。
- 开发模式关闭返回 404。
- 开发凭证错误返回 401。
- 多次开发登录复用同一 principal。
- 游客不能升级为开发人员。
- Thread CRUD owner 校验。
- 跨游客资源统一返回 404，避免泄露资源是否存在。
- 删除 Thread 清理 checkpoint。
- 活动 Thread 不能删除。
- 单 principal 活动任务锁冲突。
- 不同 principal 可以各自运行一个任务。

## 10. 已确认结论

1. 身份 session 使用 `HttpOnly + SameSite=Strict` Cookie；API Key 不进入 Cookie，本阶段也不实现 API Key 注入。
2. 游客 session 有效期 30 天，并在访问时滚动续期。
3. 开发人员填写一次独立 `IA_DEV_ACCESS_TOKEN`，开发 session 有效期 12 小时。
4. 从开发人员切回游客时，优先恢复切换前的游客身份；原 session 失效时才创建新游客。
5. LangGraph state 与长期记忆 Store 的 `user_id` 统一由服务端 principal ID 提供，不再信任请求体的 `user_id`。

用户已批准阶段 1 正式实现。
