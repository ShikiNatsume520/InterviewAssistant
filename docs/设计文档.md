# 基于 LangGraph 的多智能体 Agent 学习与简历优化系统 — 完整设计文档 (V3)

## 1. 核心需求梳理 (Requirement Analysis)

本项目定位为一个能体现 **Agent Engineering (智能体工程)** 深度和规范性的本地 MVP。本项目制作的 Agent 系统专注于**辅助用户进行 “Agent” 领域的相关知识学习问答**，以及**辅助编写与优化简历**。

### 1.1 功能性需求大纲

#### 1. 基础问答与信息追踪（第一阶段 MVP 核心）
1.  **Markdown 统一格式化与索引维护**：
    *   用户输入的非结构化/多模态文本由后端统一解析转换为标准 Markdown 格式并存储在本地知识库目录下。
    *   **索引 Agent (Index Agent)**：在导入新 Markdown 数据或检测到文件变更时运行，扫描文件内容，维护一个全局的“结构化索引文件”（`index.json`），记录关键词、主题标签、文件名以及对应的起始/结束行号。
2.  **多路混合检索 (Hybrid Retrieval)**：
    *   **向量检索 (Dense Retrieval)**：对 Markdown 文本块进行语义向量化检索。
    *   **索引文件检索 (Index Lookup)**：基于 `index.json` 进行关键词精确映射，提取相关度高的段落行区间。
    *   **Grep 文本检索 (Sparse Search)**：在本地 Markdown 目录执行正则/关键词匹配，确保最新、最精确的信息不被遗漏。
    *   **去重与重排 (De-duplication & Re-ranking)**：检索 Agent 汇总上述三路结果，通过重合行区间合并算法进行去重，并利用轻量级重排逻辑输出最相关的上下文。若检索结果得分均低于阈值，则将当前主题记录为“知识缺口（`gap_topic`）”。
3.  **精准行号引用来源追踪 (Line-level Citations)**：
    *   知识库数据切片时，必须在 Metadata 中严格保留其在原始 Markdown 文件中的真实起始行和结束行（例如：`start_line: 45, end_line: 60`）。
    *   检索 Agent 返回的每条上下文都必须附带 `[文件名](行号 ~ 行号)`。
4.  **Router 架构主图**：
    *   主图的决策中枢支持动态加载子智能体列表。根据用户请求，结构化地决定是：**直接回复**、**调用本地工具**，还是**启用子 Agent（如 RAG 子图）**。

#### 2. 智能体高阶能力（第二阶段要求，第一阶段预留接口）
*   **用户长期记忆 (Long-Term Memory)**：跨会话提取用户画像（如“目前正在学习 LangGraph 状态管理”、“简历缺少 Agent 评估经验”），持久化于本地 `Store`。
*   **知识缺口识别与自主资料扩展 (Deep Research with HITL)**：
    *   当检索 Agent 识别出 `gap_topic` 时，生成深研检索词与大纲。
    *   通过 `interrupt()` 挂起主图，前端展示深研方案，等待用户批准（HITL）。
    *   用户批准后，自主深研 Agent 迭代搜索外部网页，生成新 Markdown 文件灌入知识库，并触发 **Index Agent** 重构索引。

---

## 1.2 技术与架构性需求

*   **完全的状态隔离 (State Isolation)**：主图仅通过预留的通道（Slots）与子图交互，主图与子图状态数据不发生直接交叉污染。
*   **支持动态注册的路由中枢**：主图启动时，可根据可用子智能体配置文件，动态完成子图节点的声明、图拓扑的构建以及 Prompt 的组装。
*   **本地 SQLite 持久化**：利用 `SqliteSaver` 记录会话断点（Checkpointer），方便本地 Debug 与状态回溯。

## 3. 状态与状态转换设计 (State & Interfaces)

### 3.1 主图状态设计 (`MainState`)

```python
from typing import Annotated, List, Dict, Any, Optional, Literal
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages
from langchain_core.messages import BaseMessage

# RAG 输入输出 DTO（数据传输对象）
class RAGSubgraphInput(TypedDict):
    query: str
    search_type: Literal["embedding", "Index", "both"]

class RAGSubgraphOutput(TypedDict):
    retrieved_chunks: List[Dict[str, Any]] # 包含：content, file_path, start_line, end_line, score
    gap_topic: Optional[str]               # 若发现知识缺口，则填入缺口主题

# 深研输入输出 DTO
class ResearchSubgraphInput(TypedDict):
    gap_topic: str

class ResearchSubgraphOutput(TypedDict):
    approval_status: Literal["pending", "approved", "rejected"]
    final_knowledge_summary: str

class MainState(TypedDict):
    # 会话历史
    messages: Annotated[list[BaseMessage], add_messages]
    
    # 结构化引用源列表：最后统一渲染展示
    citations: List[Dict[str, Any]]
    
    # === 预留子智能体输入/输出通道 (Isolated I/O Slots) ===
    rag_subgraph_input: Optional[RAGSubgraphInput]
    rag_subgraph_output: Optional[RAGSubgraphOutput]
    
    research_subgraph_input: Optional[ResearchSubgraphInput]
    research_subgraph_output: Optional[ResearchSubgraphOutput]
    
    # 全局会话配置
    user_id: str
    thread_id: str
```

### 3.2 子图 1: RAG 与面经检索智能体 (`RAGState`)

*   **子图职责**：
    对用户 Query 执行三路检索（**向量数据库检索** + **`index.json`精确匹配** + **本地 Markdown 文件的 Grep 正则匹配**），将检索到的行区间进行去重与重排。如果所有通路得分低于设定的置信度阈值，则判定存在“知识缺口”，输出 `gap_topic`。

*   **子图 State Schema**：
```python
class RAGState(TypedDict):
    # 输入层：由主图通道注入
    query: str
    search_type: str # "embedding" | "Index" | "both"
    
    # 内部检索工作流变量
    vector_results: List[Dict[str, Any]]  # {"file": str, "lines": (int, int), "text": str, "score": float}
    index_results: List[Dict[str, Any]]   # 从 index.json 查找到的对应行段落
    grep_results: List[Dict[str, Any]]    # 本地目录正则扫描结果
    
    # 去重重排后的候选结果
    merged_docs: List[Dict[str, Any]]
    
    # 输出层：输出给主图
    citations_output: List[Dict[str, Any]]
    gap_topic: Optional[str]
```

*   **主图包装函数（Wrapper Node inside Node Calling Pattern）**：
```python
from langchain_core.messages import SystemMessage
from langgraph.types import RunnableConfig

def call_rag_subgraph_node(state: MainState, config: RunnableConfig):
    rag_in = state.get("rag_subgraph_input")
    if not rag_in:
        return {}
    
    # 1. 组装子图输入，调用独立的 RAG 子图
    sub_input = {
        "query": rag_in["query"],
        "search_type": rag_in["search_type"]
    }
    
    # 2. 同步唤醒子图（继承 Checkpoint 链）
    sub_output = rag_subgraph.invoke(sub_input, config)
    
    # 3. 如果判定有知识缺口，在写入输出的同时，顺便为第二阶段的“深研”槽位预备数据
    gap_topic = sub_output.get("gap_topic")
    research_input_preset = {"gap_topic": gap_topic} if gap_topic else None
    
    # 4. 构建对 LLM 的系统反馈信息（将检索内容格式化为 Markdown 注入 SystemMessage）
    formatted_context = "【检索到的本地知识库内容（严格参考以下信息回答，严禁幻觉）】:\n"
    for idx, doc in enumerate(sub_output["citations_output"]):
        formatted_context += (
            f"文献 [{idx+1}]: {doc['file_path']} (第 {doc['start_line']} ~ {doc['end_line']} 行)\n"
            f"内容: {doc['content']}\n"
            f"-------------------\n"
        )
    
    # 5. 返回更新：将格式化上下文作为 SystemMessage 插入对话，并写入输出槽位
    return {
        "messages": [SystemMessage(content=formatted_context)],
        "rag_subgraph_output": {
            "retrieved_chunks": sub_output["citations_output"],
            "gap_topic": gap_topic
        },
        # 如果有缺口，可以预填到深研输入槽中以备后续节点使用
        "research_subgraph_input": research_input_preset
    }
```

## 4. 主图 `chat_node` 结构化决策与动态节点声明

为了在主图中优雅地管理多个子智能体，且保证 `chat_node` 的推理结构化（区分**直接回复**、**调用本地普通工具**、**唤醒子智能体**），我们设计了**基于 Pydantic 强类型输出的动态总线架构**。

### 4.1 动态构建子智能体注册机制 (Dynamic Sub-Agent Registry)

我们通过一个 Python 注册类来管理子图。它将自动组装主图 Prompt 的 System 说明，并动态向 `StateGraph` 中注册对应的 wrapper 节点和连线：

```python
from typing import Callable, Dict
from pydantic import BaseModel, Field

# 1. 定义子智能体注册元数据
class SubAgentMetaData(BaseModel):
    name: str
    description: str
    wrapper_node_fn: Callable  # 主图中的包装节点函数
    input_slot_name: str       # 例如 "rag_subgraph_input"
    output_slot_name: str      # 例如 "rag_subgraph_output"

class AgentRegistry:
    def __init__(self):
        self.registry: Dict[str, SubAgentMetaData] = {}
        
    def register(self, metadata: SubAgentMetaData):
        self.registry[metadata.name] = metadata
        
    def generate_system_instruction(self) -> str:
        """动态生成注入主图 Prompt 的子智能体列表说明"""
        instruction = "【你可以唤醒的子智能体列表】:\n"
        for name, meta in self.registry.items():
            instruction += f"- 子智能体名: `{name}`\n  职责描述: {meta.description}\n\n"
        return instruction
```

### 4.2 `chat_node` 结构化决策输出设计

为了保证 `chat_node` 能够稳定地在三种职责中切换，利用 LLM 的 Structured Output 强制其输出以下格式：

```python
from pydantic import BaseModel, Field
from typing import Optional, Dict, Any, Literal

class AgentAction(BaseModel):
    # LLM 决策类型
    action_type: Literal["chat", "tool", "sub_agent"] = Field(
        ..., 
        description="决策类型。'chat'表示直接回复用户；'tool'表示调用本地普通工具；'sub_agent'表示需要将任务移交给子智能体处理"
    )
    
    # 场景 1: 直接回复
    direct_reply: Optional[str] = Field(
        None, 
        description="如果是直接回复(action_type='chat')，在此处填写最终的应答内容。如果是简历优化，请给出修改后的具体简历片段建议。"
    )
    
    # 场景 2: 调用普通工具
    tool_name: Optional[str] = Field(None, description="要调用的本地工具名称")
    tool_args: Optional[Dict[str, Any]] = Field(None, description="本地工具执行参数")
    
    # 场景 3: 唤醒子智能体
    sub_agent_name: Optional[str] = Field(
        None, 
        description="要唤醒的子智能体名称，必须是 ['rag_agent', 'research_agent'] 之一"
    )
    sub_agent_args: Optional[Dict[str, Any]] = Field(
        None, 
        description="传递给子智能体的参数。如 rag_agent 需要 {'query': 'xxx', 'search_type': 'both'}"
    )
```

**`chat_node` 节点实现**：
```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

def chat_node(state: MainState, registry: AgentRegistry):
    llm = ChatOpenAI(model="gpt-4o", temperature=0.1)
    # 强制结构化输出
    structured_llm = llm.with_structured_output(AgentAction)
    
    # 动态组装 Prompt
    sub_agent_prompt = registry.generate_system_instruction()
    system_prompt = (
        "你是一个顶级的 Agent 领域导师兼专业简历优化专家。\n"
        "请根据当前的上下文，决定下一步行动。\n"
        f"{sub_agent_prompt}\n"
        "如果用户的问题涉及专业 Agent 知识检索或简历模版匹配，请务必唤醒 `rag_agent` 子智能体检索知识库，严禁凭空编造。"
    )
    
    prompt = ChatPromptTemplate.from_messages([
        ("system", system_prompt),
        ("placeholder", "{messages}")
    ])
    
    chain = prompt | structured_llm
    # 执行决策
    decision: AgentAction = chain.invoke({"messages": state["messages"]})
    
    # 将决策结果暂时包装成一个特殊的临时 AI 消息存入 state，供之后的 dispatcher 解析
    # 我们可以在消息中带上结构化的 decision 元数据
    temp_ai_message = BaseMessage(
        content=decision.direct_reply or f"正在启动: {decision.sub_agent_name or decision.tool_name}",
        type="ai",
        additional_kwargs={"decision": decision.model_dump()}
    )
    
    return {"messages": [temp_ai_message]}
```

### 4.3 动态声明与参数分发 (`tool_dispatcher_node`)

根据结构化决策，自动将参数填入对应的 Input 槽：

```python
def tool_dispatcher_node(state: MainState, registry: AgentRegistry):
    last_msg = state["messages"][-1]
    decision_dict = last_msg.additional_kwargs.get("decision", {})
    if not decision_dict:
        return {}
        
    action_type = decision_dict.get("action_type")
    
    # 基础更新结构：默认清空所有槽位
    updates = {
        "rag_subgraph_input": None,
        "research_subgraph_input": None
    }
    
    if action_type == "sub_agent":
        agent_name = decision_dict.get("sub_agent_name")
        agent_args = decision_dict.get("sub_agent_args", {})
        
        # 从注册表中寻找对应的配置
        if agent_name in registry.registry:
            meta = registry.registry[agent_name]
            # 动态填充主图对应的 Input 槽位
            updates[meta.input_slot_name] = agent_args
            
    return updates
```

### 4.4 动态构建主图拓扑连线 (Dynamic Edge Router)

利用 Pydantic 提取出的状态槽更新来决定路由流向：

```python
def main_dynamic_router(state: MainState, registry: AgentRegistry):
    # 遍历注册表，检查哪个 Input 槽有输入数据
    for agent_name, meta in registry.registry.items():
        if state.get(meta.input_slot_name) is not None:
            # 路由到对应的包装节点
            return f"call_{agent_name}_node"
            
    # 如果所有输入槽都为空，说明是一般回复，流向保存记忆节点并结束
    return "save_memory_and_end"
```

在图构建阶段，我们可以**根据注册表自动循环连接节点**，实现完全可拔插的工程化设计：

```python
from langgraph.graph import StateGraph, END

def build_main_graph(registry: AgentRegistry):
    workflow = StateGraph(MainState)
    
    # 1. 添加基础节点
    workflow.add_node("load_memory_node", load_memory_node)
    workflow.add_node("chat_node", lambda state: chat_node(state, registry))
    workflow.add_node("tool_dispatcher_node", lambda state: tool_dispatcher_node(state, registry))
    workflow.add_node("save_memory_and_end", save_memory_and_end_node)
    
    # 2. 动态加载子智能体节点
    for name, meta in registry.registry.items():
        # 添加主图中的 wrapper 节点
        node_name = f"call_{name}_node"
        workflow.add_node(node_name, meta.wrapper_node_fn)
        # 连接该包装节点回 chat_node
        workflow.add_edge(node_name, "chat_node")
    
    # 3. 构建核心连线
    workflow.set_entry_point("load_memory_node")
    workflow.add_edge("load_memory_node", "chat_node")
    workflow.add_edge("chat_node", "tool_dispatcher_node")
    
    # 4. 动态路由边
    workflow.add_conditional_edges(
        "tool_dispatcher_node",
        lambda state: main_dynamic_router(state, registry),
        # 路由映射表
        path_map={
            **{f"call_{name}_node": f"call_{name}_node" for name in registry.registry},
            "save_memory_and_end": "save_memory_and_end"
        }
    )
    
    workflow.add_edge("save_memory_and_end", END)
    return workflow
```

## 5. 存储层方案 (Local Storage Layer)

为了达成在本地容易复现和排查的非目标条件，存储层配置如下：

1.  **Checkpointer (运行状态恢复数据库)**：
    *   使用 `SqliteSaver`，将全局图和子图执行状态、分支路由轨迹持久化至 `sqlite_checkpoints.db`。通过 `thread_id` 可以重建整个事件序列，轻松排查崩溃现场。
2.  **Store (长期记忆数据库)**：
    *   使用基于本地 SQLite 的持久化 `Store`（或 LangGraph 提供的支持持久化的 `BaseStore`）。存储用户的长期画像和累积技术薄弱点。
3.  **Vector DB (向量库)**：
    *   使用本地 **Chroma** 数据库（轻量、无外部服务依赖），配置 `domain_kb` 和 `interview_kb` 两个 Collections。

## 6. 增量式工程开发与测试流程 (Incremental Pipeline)

系统开发将按照以下生命周期模型迭代进行，并在每个周期通过 LangGraph Studio 进行可视化验证。

```
 ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
 │ Phase 1:        │     │ Phase 2:        │     │ Phase 3:        │
 │ 混合 RAG 子图   ├────>│ 动态主图总线    ├────>│ 长期记忆与      │
 │ (本地检索与去重)│     │ (结构化决策路由)│     │ 简历优化模板    │
 └─────────────────┘     └─────────────────┘     └─────────────────┘
                                                          │
                                                          ▼
 ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
 │ 后续路线:       │     │ Phase 5:        │     │ Phase 4:        │
 │ 自主外部深研    │<────│ FastAPI 端到端  │<────│ 本地 SQLite     │
 │ (HITL 人机协同) │     │ 接口挂载与集成  │     │ 状态断点排查    │
 └─────────────────┘     └─────────────────┘     └─────────────────┘
```

### 第一阶段：混合 RAG 与索引维护子图 (RAG Subgraph Validation)
1.  **开发内容**：
    *   实现**索引 Agent**：编写脚本扫描本地 `/data/markdown` 目录，遍历行区间建立关键词到文件的映射，写出 `index.json`。
    *   构建 `RAG 子图`：定义向量相似检索函数、`index.json` 快速查找函数、以及 Python `re` 模块实现的本地 Markdown `grep` 函数。
    *   编写重排与去重合并算法（重合行合并，如 [10, 20] 与 [15, 25] 合并为 [10, 25]），输出含精准引用的候选集。
2.  **Studio 测试**：
    *   在 `langgraph.json` 中配置 RAG 子图入口，启动 LangGraph Studio。
    *   手动输入 `{ "query": "LangGraph 的 State 如何定义", "search_type": "both" }`，查看 Graph 内部检索变量的值，确保返回的 `citations_output` 包含文件行数。

### 第二阶段：动态主图与结构化决策集成 (Main Graph Integration)
1.  **开发内容**：
    *   实现 `AgentRegistry` 类。
    *   编写 `chat_node` 的 Pydantic Structured Output 控制，确保能稳定生成 `AgentAction` 结构体。
    *   编写 `tool_dispatcher_node` 进行参数分发。
2.  **Studio 测试**：
    *   在 Studio 中输入问题：“你好，请帮我看看我的 Agent 简历模版中有什么需要优化的，或者帮我查查本地有什么简历模板。”
    *   观察主图执行轨迹：主图进入 `chat_node` -> 决策生成唤醒 `rag_agent` -> 分发节点将参数送入 `rag_subgraph_input` -> 触发子图包装节点 -> 完成本地简历模板检索 -> 返回 `ToolMessage` 系统上下文 -> `chat_node` 生成最终修改建议。

### 第三阶段：本地存储、断点保存与 FastAPI 接口部署
1.  **开发内容**：
    *   引入 `SqliteSaver` 连接本地 SQLite 数据库，编译主图。
    *   使用 FastAPI 封装接口 `/v1/chat`（接收 `user_id` 与 `thread_id`），支持流式 SSE 输出。
2.  **测试验证**：
    *   使用 Postman/Python 脚本多次调用 `/v1/chat`。
    *   **故障模拟测试**：在 RAG 检索子图中间强行中断网络/程序报错，查看 `sqlite_checkpoints.db`。获取最后的 `checkpoint_id`，利用测试脚本调用 `app.get_state_history()` 重放崩溃前的状态，确认整个多智能体系统能够无缝继续执行（State Replay）。

## 7. 开放性提问与技术核对 (Feedback & Questions)

在开始具体的代码编写前，有以下两个关键设计细节需要向您确认，以便将方案设计得更贴合您的工程预期：

1.  **Grep 检索的具体范围与深度**：
    *   本地 Markdown 知识库的大小预计处于什么量级（几十个文件还是上百个）？如果文件量较大，在每次用户提问时都实时执行 Python 的 Grep 全文正则扫描可能会带来明显的 I/O 延迟。我们是否应该仅在**“向量检索出相关文件后，针对这些特定文件进行精确 Grep 匹配”**，还是保持对全目录下文件的并行 Grep？
2.  **简历优化场景的交互机制**：
    *   在进行“简历优化”时，用户通常会上传一整段个人经历。针对这一场景，我们是否需要提供一个**“简历对比与草稿暂存”**的局部状态，还是说直接让用户在 `messages` 中与 LLM 进行多轮对话修改，仅在结束时由记忆 Agent 提取优化点存入 Store 即可？
