# Interview Assistant 部署上线方案书

## 1. 文档目的

本文给出 Interview Assistant 从本地开发环境走向公网部署的完整方案，包括：

- 当前系统的部署边界与数据流；
- 已具备的安全能力；
- 上线前仍需修补的安全风险；
- 可选托管方式及适用场景；
- 推荐的首版生产架构；
- 上线实施、验收、备份、监控与回滚流程。

本文以当前代码版本 `c6c4972` 为基线。第一版目标是小规模、单实例、桌面浏览器可用的公开服务，不以高并发、多区域或企业级容灾为目标。

## 2. 当前系统概况

### 2.1 产品能力

当前系统包含：

- React 单页前端；
- FastAPI HTTP/SSE 服务；
- LangGraph 主图与 RAG、Resume、Research 等子智能体；
- 游客身份与会话隔离；
- 用户自行配置模型 API Key；
- Thread、产品事件、checkpoint 与长期记忆持久化；
- Markdown 简历上传、管理、修改和下载；
- 公共知识与个人知识管理；
- 深度研究、Interrupt 审批、中断恢复和知识入库确认；
- 仅供本地调试的开发人员登录模式。

### 2.2 当前运行方式

前端先构建到 `frontend/dist`，再由 FastAPI 同源托管：

```text
浏览器
  │
  ├─ GET /、/assets/*          React 静态资源
  ├─ /v1/*                    JSON API
  └─ /v1/chat、/v1/checkpoint SSE 长连接
        │
        ▼
单进程 FastAPI + LangGraph
        │
        ├─ data/state/*.sqlite
        ├─ data/chroma/
        ├─ data/markdown/
        ├─ data/knowledge/
        └─ 外部模型与搜索服务
```

同源部署是当前最合适的方式：不需要额外改造 CORS、跨域凭据 Cookie 和前端 `/v1/*` 地址，SSE 也只经过一条公开域名链路。

### 2.3 持久化资产

生产环境必须持久化并备份整个 `data/`，其中至少包括：

| 路径 | 内容 | 丢失后影响 |
|---|---|---|
| `data/state/app.sqlite` | 身份、会话、Thread、产品事件、简历与知识元数据、操作账本 | 用户无法恢复原有产品数据 |
| `data/state/checkpoints.sqlite` | LangGraph checkpoint | 中断任务和子智能体状态无法恢复 |
| `data/state/store.sqlite` | LangGraph 长期记忆 | 长期记忆丢失 |
| `data/chroma/` | 公共知识向量数据 | RAG 向量检索不可用或不完整 |
| `data/knowledge/` | 个人知识隔离目录及向量数据 | 用户个人知识丢失 |
| `data/markdown/` | 公共知识 Markdown 与元数据 | 公共知识原文丢失 |
| `data/index.md` | 关键词索引 | 关键词检索结果不完整 |

SQLite 可能使用 WAL 模式。不能在数据库持续写入时只复制主 `.sqlite` 文件；应使用 SQLite 在线备份能力、短暂停写后整体快照，或由平台对整个持久卷制作一致快照。

## 3. 已具备的安全基础

以下能力已经存在，但不能替代后续加固：

1. `.env`、SQLite 和 Chroma 等运行数据已被 `.gitignore` 排除；当前 Git 历史未发现真实格式的 API Key。
2. 游客资源以 `principal_id` 隔离，简历、个人知识和 Thread 查询均由后端身份决定，不接受前端自由指定用户 ID。
3. 身份 Cookie 使用 `HttpOnly` 和 `SameSite=Strict`。
4. 设置 `IA_COOKIE_SECURE=true` 后，身份 Cookie 只通过 HTTPS 发送。
5. `IA_DEV_MODE=false` 时：
   - `/v1/capabilities` 不向前端声明开发登录能力；
   - 前端不显示开发人员入口；
   - `/v1/identity/developer` 后端接口直接返回 404。
6. 游客 API Key 保存在当前标签页的 `sessionStorage`，不会写入应用数据库、产品事件或 LangGraph checkpoint。
7. 非本机环境提交 API Key 时，后端要求当前请求使用 HTTPS；模型 Provider 地址也要求 HTTPS。
8. Resume 上传在后端已有 1 MiB 限制，不能仅依赖前端校验。
9. Interrupt 使用稳定 `interrupt_id`，HTTP 操作使用 `operation_id`，可以避免审批串用和重复恢复。
10. 当前 Thread 对执行任务有互斥控制，避免同一身份并发修改同一运行状态。

## 4. 上线前安全风险与修补要求

### 4.1 P0：必须修复，否则不应公开上线

#### 4.1.1 自定义模型地址可能形成 SSRF

现状：游客可以提交模型 `base_url`，FastAPI 随后从服务器访问该地址。当前只检查 URL 格式及 HTTPS，仍不足以阻止攻击者访问云平台元数据地址、内网 HTTPS 服务、DNS 重绑定目标或经重定向进入内网。

风险：

- 探测服务器内网与私有服务；
- 尝试访问云平台实例元数据；
- 利用服务器网络身份访问用户本来不可访问的地址；
- 让服务端建立大量慢连接，消耗连接池和任务资源。

首版推荐修复：生产模式只开放受信任 Provider 预设，不允许自定义 Base URL。后端维护精确的协议、域名和端口白名单，不能只由前端限制。

若未来恢复自定义地址，至少需要：

- 只允许 HTTPS；
- DNS 解析后拒绝回环、私网、链路本地、保留地址和云元数据网段；
- 每次重定向重新校验目标，或直接禁止重定向；
- 限制端口；
- 设置连接、读取和总请求超时；
- 限制响应大小；
- 防御 DNS 重绑定，并在实际连接地址层执行校验。

#### 4.1.2 缺少系统级限流和滥用控制

现状：已有 principal 级活动任务互斥，但没有完整的 IP、身份和接口级速率限制。

风险：攻击者可以反复创建游客、会话、深研任务、索引任务或大量产品事件，消耗 CPU、网络、搜索服务和磁盘。即使模型费用由用户自己的 Key 承担，服务器资源仍由平台承担。

上线前至少增加：

- 每 IP 的游客身份创建速率限制；
- 每 IP 与每 principal 的普通 API 请求限制；
- 每 principal 同时只能运行一个图任务；
- 深度研究单独设置更严格的分钟/小时额度；
- 上传、重建索引和模型连接测试单独限流；
- 对 429 返回稳定错误码和 `Retry-After`；
- 在反向代理和应用层同时设置基础限制。

单实例首版可以使用进程内令牌桶，但重启会清空、未来不能支持多实例。更成熟的方案应使用 Redis 等共享限流存储。

#### 4.1.3 所有上传和请求体必须有后端硬限制

现状：Resume 已有后端 1 MiB 限制；知识上传的 Pydantic 字段限制了非空和名称长度，但未见等价的正文总字节硬上限。反向代理层也尚未配置请求体限制。

风险：超大 JSON 请求会在进入业务校验前占用内存；知识索引还可能放大 CPU、Embedding 请求和磁盘消耗。

建议：

- Nginx/Caddy/平台入口限制请求体，例如 1–2 MiB；
- FastAPI 再对 UTF-8 编码后的知识正文实施字节限制；
- 限制 Markdown 行数、字符数和单用户总存储量；
- 限制单用户知识条目、简历和 Thread 数量；
- 上传失败时不遗留半写文件、元数据或向量块。

#### 4.1.4 生产密钥与开发模式必须彻底隔离

生产环境必须：

```env
IA_DEV_MODE=false
IA_COOKIE_SECURE=true
```

并满足：

- 不把 `.env` 放入镜像、前端产物或 Git；
- 不在生产环境设置可用的 `IA_DEV_ACCESS_TOKEN`，即使接口已经关闭；
- 使用托管平台 Secret 或服务器权限受限的环境文件；
- 不在日志中打印请求头、模型配置或异常对象里的 API Key；
- 对历史上曾公开、截图或发送过的真实 Key 直接轮换。

隐藏前端入口本身不构成安全边界；真正的安全边界是后端在 `IA_DEV_MODE=false` 时拒绝该接口。当前代码已经做到这一点，部署配置必须保持关闭。

#### 4.1.5 必须强制 HTTPS

游客 API Key 会作为请求头到达后端。它不会写入数据库，但后端必须在内存中读取后才能调用模型服务。因此“绝不经过后端”与当前代理式架构不兼容；实际安全目标应是：只在浏览器当前会话和后端当前请求内短暂存在，全程通过 TLS 传输，不进入持久化和日志。

要求：

- 公网 HTTP 永久重定向到 HTTPS；
- `IA_COOKIE_SECURE=true`；
- 开启 HSTS；
- Provider Base URL 只允许 HTTPS；
- TLS 在受信任反向代理或平台入口终止；
- 只信任来自该代理的转发协议头，防止伪造 `X-Forwarded-Proto` 绕过 HTTPS 判断。

### 4.2 P1：首版上线强烈建议完成

#### 4.2.1 浏览器 API Key 仍受 XSS 威胁

`sessionStorage` 比长期 Cookie 或后端数据库更符合当前产品目标，但同源 JavaScript 一旦发生 XSS，仍可读取 API Key。

需要：

- 设置严格 CSP，至少限制 `script-src`、`connect-src`、`object-src`、`base-uri` 和 `frame-ancestors`；
- 禁止不必要的内联脚本与第三方脚本；
- 固定前端依赖版本并审查供应链更新；
- 保持 Markdown 渲染清洗，新增富文本功能时不得绕过 sanitize；
- 增加 `X-Content-Type-Options: nosniff`、`Referrer-Policy` 和点击劫持防护；
- 模型配置界面明确说明关闭标签页或清除配置的行为。

#### 4.2.2 缺少 Trusted Host 与明确的反向代理信任边界

应限制服务接受的 Host，避免 Host Header 被用于生成错误外部地址或污染日志。Uvicorn 不应直接暴露管理端口，只允许反向代理或云平台入口访问。

建议：

- 配置允许域名列表；
- 仅信任明确代理 IP/网络的 forwarded headers；
- 应用监听容器内部或 `127.0.0.1`，公网只开放 80/443；
- 禁止暴露 LangGraph Studio、调试端口和内部数据库文件。

#### 4.2.3 错误响应与日志信息泄露

生产环境不应返回 Python traceback、文件绝对路径、数据库异常文本、模型服务完整响应或请求头。

建议：

- 用户响应只返回稳定错误码和可公开消息；
- 详细异常写入受控日志，并对 API Key、Cookie、Authorization、自定义模型请求头脱敏；
- 设置日志保留时间与文件大小轮转；
- 为每次请求或任务增加不含敏感信息的关联 ID。

#### 4.2.4 游客身份生命周期与数据清理

游客当前没有注册登录，浏览器 Cookie 丢失后无法重新找回原 principal，但服务器仍保存其数据。

上线前需要确定并实现：

- 游客 Session 有效期；
- 无活动游客数据保留期，例如 7、30 或 90 天；
- Thread、checkpoint、产品事件、简历、个人知识、向量数据必须按 principal 一致清理；
- 清理任务失败时可重试并可审计；
- 页面展示隐私与数据保留说明。

#### 4.2.5 SSE、超时和连接资源控制

反向代理需要：

- 关闭 SSE 响应缓冲；
- 配置足够长但有限的读取超时；
- 设置单 IP 长连接上限；
- 客户端断开后及时取消后端任务；
- 禁止 CDN 把用户 SSE 或 JSON 响应公开缓存。

### 4.3 P2：可以在上线后持续完善

- Redis/队列化任务和跨进程取消；
- PostgreSQL 替换部分 SQLite 元数据；
- 对象存储保存简历与 Markdown；
- 托管向量数据库替代本地 Chroma；
- 多副本、灰度发布和自动扩缩容；
- 注册登录、账号找回和用户主动注销；
- 安全审计日志、告警和异常行为检测；
- 依赖漏洞扫描、SBOM、镜像签名与自动补丁流程；
- 数据导出、删除请求和隐私合规流程。

## 5. 托管上线方式比较

### 5.1 代码托管到 GitHub

可以，也推荐使用 GitHub 托管代码，但首版建议使用私有仓库。

GitHub 的职责是：

- 保存代码与版本历史；
- Pull Request 和代码审查；
- GitHub Actions 执行测试、构建镜像或触发部署；
- Secret Scanning/Push Protection 减少密钥误提交风险。

GitHub 不应保存：

- `.env`；
- 用户数据库和 checkpoint；
- Chroma 数据目录；
- 用户简历和个人知识；
- 生产日志与备份。

推送前应启用 Push Protection，并检查完整 Git 历史。GitHub 官方说明：Push Protection 会在推送阶段阻止检测到的硬编码凭据：<https://docs.github.com/en/code-security/concepts/secret-security/push-protection>。

### 5.2 GitHub Pages

不适合托管完整产品。GitHub Pages 是静态站点托管，只能发布构建后的 HTML、CSS 和 JavaScript，不运行 FastAPI/Python：<https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site>。

理论上可以把 React 放到 Pages、后端放到其他平台，但当前项目需要额外改造：

- 前端 API Base URL；
- CORS；
- 跨域 Cookie 与 `SameSite` 策略；
- CSRF 防护；
- SSE 跨域链路；
- CSP `connect-src`；
- 两个域名的部署和故障排查。

第一版没有必要承担这些复杂度，因此不推荐前后端分离托管。

### 5.3 Render 或类似 PaaS

适合希望快速上线、不想维护 Linux 主机的场景。

优点：

- 可连接 GitHub 自动部署；
- 托管 HTTPS 和自定义域名；
- 环境变量/Secret 管理；
- 健康检查和日志；
- 可以附加持久化磁盘。

缺点：

- 持久磁盘通常需要付费；
- 磁盘绑定服务实例，扩展多副本受限；
- 休眠、部署重启、区域和资源限制需按套餐确认；
- 本项目仍必须保持单实例、单 worker。

Render 默认文件系统是临时的，只有持久磁盘挂载路径下的数据会保留：<https://render.com/docs/disks>。如果使用 Render，应将持久盘挂载到应用的 `data/` 目录，例如 Docker 工作目录为 `/app` 时挂载 `/app/data`。

Railway、Fly.io 等平台也可采用相似结构，但选择前必须确认：持久卷、SSE 长连接、休眠策略、出站网络、备份方式和单实例部署能力。

### 5.4 云服务器/VPS + Docker

适合希望掌握数据、网络和备份策略，并愿意维护服务器的场景。

推荐组件：

```text
Ubuntu LTS
├─ Caddy 或 Nginx：HTTPS、域名、限流、安全头、SSE 代理
├─ Interview Assistant 容器：单进程 Uvicorn
└─ /srv/interview-assistant/data：宿主持久化目录
```

优点：

- 对磁盘、备份、防火墙和日志控制最完整；
- 成本结构清楚；
- 当前 SQLite + Chroma 本地持久化模式容易落地。

缺点：

- 需要自行维护系统更新、防火墙、TLS、监控、磁盘和备份；
- 错误配置可能比 PaaS 风险更高；
- 需要处理容器更新与回滚。

### 5.5 容器平台/Kubernetes

当前不推荐。系统依赖本地 SQLite、Chroma 和进程内任务注册表，尚未具备真正的多副本共享状态。过早引入 Kubernetes 只会增加卷调度、会话黏性、任务协调和运维复杂度。

## 6. 推荐的第一版生产方案

### 6.1 推荐选择

推荐按团队运维能力二选一：

1. 最快上线：GitHub 私有仓库 + Render 单实例 Web Service + Persistent Disk。
2. 更强控制：GitHub 私有仓库 + 单台 VPS + Docker + Caddy + 宿主持久化目录。

两种方案都使用前后端同域、单进程 FastAPI，不使用 GitHub Pages。

### 6.2 生产构建流程

建议使用多阶段 Docker 构建：

1. Node 构建阶段安装前端锁定依赖并执行 `npm run build`；
2. Python 运行阶段使用 `uv.lock` 安装锁定依赖；
3. 只复制源码、`frontend/dist` 和必要的 Lapis 静态资源；
4. 不复制 `.env`、日志、测试数据、本地数据库和缓存；
5. 以非 root 用户运行；
6. 将 `/app/data` 声明为持久化挂载点；
7. 启动一个 Uvicorn worker，不使用 `--reload`。

示意启动命令：

```shell
uv run uvicorn server.app:app --host 0.0.0.0 --port ${PORT:-8000} --workers 1
```

### 6.3 生产环境变量

最低要求：

```env
IA_DEV_MODE=false
IA_COOKIE_SECURE=true
```

如果生产环境完全采用游客自带 API Key，就不应为正常网页流量配置开发者模型 Key。服务端仍可能需要 Embedding 或搜索相关凭据，必须通过平台 Secret 注入，不能写入镜像或仓库。

建议新增生产配置：

```env
IA_ENV=production
IA_ALLOWED_HOSTS=assistant.example.com
IA_ALLOWED_PROVIDER_HOSTS=api.openai.com,api.deepseek.com
IA_MAX_REQUEST_BYTES=2097152
IA_GUEST_RETENTION_DAYS=30
IA_LOG_LEVEL=INFO
```

这些变量目前不一定全部已经实现，应在上线加固阶段补齐后再用于部署。

### 6.4 反向代理要求

- HTTP 自动跳转 HTTPS；
- 自动签发和续期 TLS 证书；
- `/v1/chat`、`/v1/checkpoint` 禁止代理缓冲；
- 设置合理的连接、请求头、请求体和读取超时；
- 对静态 hash 资源设置长期缓存；
- 对 HTML、API、SSE 和用户下载资源禁用公共缓存；
- 添加 HSTS、CSP、`nosniff`、Referrer Policy 和 frame 限制；
- 限制请求速率和并发连接；
- 不暴露 Uvicorn、Studio 或调试端口。

## 7. CI/CD 与发布流程

### 7.1 GitHub 分支建议

- `main`：生产候选；
- 功能分支：日常开发；
- 通过 Pull Request 合并；
- 对 `main` 启用保护规则，要求测试通过；
- 发布版本打语义化 Tag，例如 `v1.0.0`。

### 7.2 CI 必跑项目

```shell
uv run ruff check src tests
uv run mypy --strict src
uv run python -m pytest tests/unit_tests
npm ci --prefix frontend
npm run build --prefix frontend
```

CI 不应真实调用付费模型或携带生产 API Key。需要模型的集成测试使用独立、低权限、有限额的测试凭据，并通过 GitHub Environment Secret 注入。

### 7.3 CD 建议

1. CI 通过后构建不可变容器镜像；
2. 对镜像做依赖漏洞扫描；
3. 先部署到 staging；
4. 执行健康检查与关键用户故事冒烟测试；
5. 人工批准生产发布；
6. 数据迁移或索引变更前先备份；
7. 生产发布后保留上一个镜像版本用于回滚。

## 8. 上线前实施阶段

### 阶段 A：安全阻断项修复

- Provider 后端白名单与 SSRF 防护；
- IP/principal/高成本接口限流；
- 知识上传、请求体、用户配额硬限制；
- Trusted Host、可信代理和 HTTPS 强制策略；
- CSP 与常用安全响应头；
- 日志脱敏和生产错误响应；
- 游客数据过期清理策略。

完成标准：安全回归测试通过，生产配置下开发登录接口为 404，自定义危险 Provider 地址全部被后端拒绝。

### 阶段 B：容器化与持久化验证

- 编写 Dockerfile 和 `.dockerignore`；
- 使用空白 `data/` 启动；
- 挂载持久卷；
- 重启容器后验证 Thread、checkpoint、简历与知识仍存在；
- 验证单 worker、SSE 和中断恢复。

### 阶段 C：Staging 部署

- 使用独立域名和独立数据卷；
- 设置生产同等的 HTTPS、Cookie 和代理配置；
- 使用测试 Provider Key；
- 执行完整用户故事验收；
- 做一次备份和恢复演练。

### 阶段 D：生产发布

- 创建干净生产数据目录；
- 关闭开发模式；
- 注入生产 Secret；
- 绑定正式域名；
- 开启监控、告警和备份；
- 小流量开放，观察磁盘、错误率、SSE 连接和外部 API 调用。

## 9. 上线验收清单

### 9.1 安全

- [ ] `IA_DEV_MODE=false`，前端无开发入口，开发登录 API 返回 404。
- [ ] `.env`、数据库、日志和用户文件不在 Git、镜像层或静态产物中。
- [ ] HTTP 强制跳转 HTTPS，Cookie 带 `Secure`、`HttpOnly`、`SameSite=Strict`。
- [ ] 任意自定义 Provider URL 被禁用，或已完成严格 SSRF 防护。
- [ ] 限流、请求体限制、上传限制和用户配额生效。
- [ ] CSP、安全响应头、Trusted Host 与可信代理配置生效。
- [ ] API Key 不出现在日志、产品事件、checkpoint、数据库和错误响应中。
- [ ] 公共知识管理接口只有开发身份可调用，而生产环境不存在开发身份入口。

### 9.2 功能

- [ ] 游客首次进入能建立隔离身份。
- [ ] 配置 API Key 后普通聊天与 RAG 正常。
- [ ] 多 Thread 会话隔离正常。
- [ ] 简历上传、指定、修改、审批、保存新版本与下载正常。
- [ ] 深研计划审批、搜索过程、报告展示和入库审批正常。
- [ ] 中断深研后重新进入会话，能从 checkpoint 恢复且不会跳过入库确认。
- [ ] 个人知识、简历和会话不能被其他游客身份读取。

### 9.3 运维

- [ ] 容器和服务重启后数据仍存在。
- [ ] 健康检查 `/health` 正常。
- [ ] SSE 不被代理缓冲，长任务不会因默认短超时断开。
- [ ] 单进程运行，没有误开多个 worker。
- [ ] 磁盘容量、错误率、响应时间和任务失败率有监控。
- [ ] 完整备份与恢复演练成功。
- [ ] 上一版本镜像可以快速回滚。

## 10. 监控、备份与故障恢复

### 10.1 最低监控指标

- HTTP 4xx/5xx 数量与比例；
- SSE 当前连接数和异常断开数；
- 图任务运行、等待、中断、失败数量；
- 模型连接超时和 Provider 错误率；
- 深研平均耗时、网页抓取失败率；
- SQLite 锁错误；
- 数据盘使用率、文件数与每日增长量；
- 进程内存、CPU 和重启次数。

### 10.2 备份策略

首版建议：

- 每日自动备份整个 `data/`；
- 至少保留 7 个日备份和 4 个周备份；
- 备份加密并存放在与运行实例不同的位置；
- 每月至少执行一次恢复演练；
- 发布涉及数据结构或索引改变前创建额外备份；
- 记录备份版本对应的应用 Git commit 或镜像 Tag。

### 10.3 回滚边界

代码回滚不等于数据回滚。若新版本写入了不兼容的数据结构：

1. 停止写入流量；
2. 保存故障现场数据；
3. 回滚应用镜像；
4. 按迁移兼容性决定是否恢复数据快照；
5. 验证 checkpoint、个人知识和向量索引一致性；
6. 再恢复流量。

## 11. 成本与扩展判断

第一版主要成本来自：

- 单实例计算资源；
- 持久化磁盘与备份；
- 域名；
- 搜索、Embedding 或其他服务端公共能力；
- 日志和监控。

游客自带模型 API Key 可以降低平台的模型费用，但不能消除服务器滥用、Embedding、搜索、存储和带宽成本。

出现以下任一情况时，应启动第二阶段架构升级：

- 单实例资源持续超过 60%–70%；
- SQLite 锁冲突或磁盘 I/O 成为瓶颈；
- 需要多副本或零停机扩容；
- 需要账号跨设备登录；
- 用户数据保留和合规要求提高；
- 深研任务需要排队、后台运行或跨进程取消。

升级方向是 PostgreSQL + Redis/任务队列 + 对象存储 + 托管向量库，而不是直接把当前 SQLite 文件放到多个应用副本后面。

## 12. 最终建议

1. 代码可以托管到 GitHub，首版使用私有仓库并开启 Push Protection。
2. 不使用 GitHub Pages 托管完整应用，也不在第一版拆分前后端域名。
3. 优先完成 P0 安全修复，再制作 Docker 镜像。
4. 首版部署到 Render 持久磁盘单实例，或单台 VPS 的 Docker + Caddy；根据维护能力选择。
5. 保持一个 Uvicorn worker和一个持久数据卷。
6. 先通过 staging、备份恢复演练和完整用户故事验收，再开放公网。
7. 公网生产永久关闭开发模式；LangGraph Studio 仅在本地或受控内网环境使用。
