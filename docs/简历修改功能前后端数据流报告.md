# 简历修改功能前后端数据流报告

> 目的：从用户故事出发，串联当前 React 前端、FastAPI 产品层、Main Agent、Resume Agent 子图、SQLite 资源库、产品事件时间线与 LangGraph checkpoint，便于逐段审查实现是否符合产品预期。

## 1. 当前功能定位

用户可以在一个持续的会话中：

1. 上传、查看、重命名、删除和指定 Markdown 简历；
2. 用自然语言要求 Main Agent 修改某份简历；
3. 由 Main Agent判断目标简历并调用 Resume Agent；
4. 在不刷新聊天时间线的情况下进入独立的 Resume Agent 常驻编辑会话；
5. 审阅修改计划、逐条批准或拒绝修改、提出调整建议；
6. 在 `hitl_standby` 继续提出新的修改要求；
7. 最终选择保存为一份新的派生简历，或者放弃整个工作草稿。

源简历始终只读。批准仅表示修改进入当前 checkpoint 工作草稿，不会覆盖源简历；只有“保存为新简历并退出”才会创建新的简历资源。

## 2. 两条互不替代的持久化链

### 2.1 图执行链：LangGraph checkpoint

LangGraph checkpoint 保存 Main Graph 与 Resume 子图的执行状态，包括：

- Main Agent 与 Resume Agent 的消息状态；
- 当前子图命名空间和下一节点；
- `resume_shot` 工作草稿；
- 已处理的修改项；
- 当前计划和 Interrupt；
- 保存或放弃意图。

图恢复只读取 checkpoint。任何产品事件都不会成为图输入。

### 2.2 产品展示链：产品事件时间线

产品事件用于恢复浏览器界面，包括：

- `message.user`：用户消息；
- `message.agent`：完整的可见 Agent 消息；
- `task.started/status/completed/interrupted/failed`：执行状态；
- `agent.transition`：Main/Resume Agent 交接；
- `tool.status`：工具完成状态；
- `interrupt.requested/resolved`：审批卡片和用户决策；
- `resume.result`：保存或放弃的最终结果；
- `citation.list`：知识问答实际采用的引用。

流式 token 作为临时 `delta` 发给浏览器，不逐 chunk 持久化；完整消息结束后才写入 `message.agent`。意外断线时未完成的 chunk 可以丢失。

checkpoint 重跑可能再次产生相似产品事件，前端按稳定事件 ID 和事件顺序原样展示，不做图级去重。

## 3. 从打开前端开始的完整用户故事

### 3.1 用户第一次打开页面：建立游客身份

前端入口 `frontend/src/App.tsx::App` 挂载后首先执行：

1. 调用 `GET /v1/identity`，尝试恢复已有身份；
2. 如果服务端返回 401，调用 `POST /v1/identity/guest`；
3. 后端创建一个 UUID 形式的 `Principal(kind="guest")`；
4. 后端创建随机 Session Token；
5. 数据库只保存 Token 的 SHA-256 哈希及其对应的 `principal_id`；
6. 响应通过 `Set-Cookie` 写入 `ia_session`。

Cookie 属性为：

```text
HttpOnly = true
SameSite = strict
Secure = COOKIE_SECURE（部署 HTTPS 时应为 true）
Path = /
游客有效期 = 30 天，认证请求时滚动续期
```

前端能够看到接口返回的 `principal_id` 和身份类型，但之后不会把它作为授权参数提交。真正的授权凭据是 HttpOnly Cookie 中的随机 Session Token。

如果用户清除了 Cookie 或换了设备，第一版游客模式会创建新的 principal，因此无法看到旧 principal 的简历和会话。这是游客身份的预期限制，不代表数据没有隔离。

### 3.2 浏览器后续请求如何携带身份

`frontend/src/api.ts` 的普通 JSON 请求和 SSE 请求都设置：

```ts
credentials: "same-origin"
```

浏览器因此自动携带 `ia_session`，但前端 JavaScript 因 HttpOnly 无法读取 Token。

FastAPI 端所有受保护接口使用：

```python
auth: AuthSession = Depends(current_auth)
```

`current_auth` 的处理链是：

```text
Cookie ia_session
  → _authenticate_token(token)
  → IdentityThreadStore.authenticate(token)
  → 对 token 做 SHA-256
  → sessions.token_hash 查询 principals
  → AuthSession(principal=Principal(id, kind))
```

所以后端知道当前用户是谁，不依赖请求 JSON 里的 `user_id`。

### 3.3 开发人员登录的身份差异

开发人员登录仍然会签发同样的 `ia_session` Cookie，但 principal 固定为本地开发身份 `developer-local`，并使用服务端 `.env` 模型配置。游客和开发人员之间仍然由不同 `principal_id` 隔离。

当前开发模式是单个本地开发身份，不是面向多个开发账号的认证系统。

### 3.4 创建或恢复 Thread

身份建立后，前端调用 `GET /v1/threads`。服务端实际执行：

```sql
SELECT ... FROM threads
WHERE principal_id = ?
```

参数来自 `auth.principal.id`。如果没有 Thread，用户点击新建会话后调用 `POST /v1/threads`，后端把同一个 principal 写入 `threads.principal_id`。

后续访问指定 `thread_id` 时，`_require_thread(auth.principal, thread_id)` 会再次比较 Thread 的 principal。即使用户知道别人的 Thread ID，也不能读取其事件、选择的简历或 checkpoint 入口。

### 3.5 打开简历列表

用户点击简历按钮后，前端调用 `GET /v1/resumes`。请求体不含 `user_id`，但 Cookie 会被自动带上：

```text
GET /v1/resumes
Cookie: ia_session=<随机 Session Token>
```

服务端依赖注入得到 `auth.principal.id` 后调用：

```python
_resume_repository().list(auth.principal.id)
```

`ResumeRepository.list` 最终执行：

```sql
SELECT ... FROM resumes
WHERE principal_id = ?
ORDER BY created_at DESC, rowid DESC
```

因此所有用户的记录物理上可以位于同一张 SQLite `resumes` 表中，但每条记录都有 owner，所有资源入口均按 owner 过滤或校验。这属于“共享表、行级租户隔离”，不是“所有用户共享简历”。

### 3.6 完整总体数据流

```mermaid
sequenceDiagram
    actor U as 用户
    participant F as React 前端
    participant API as FastAPI 产品层
    participant ID as IdentityThreadStore
    participant M as Main Agent
    participant R as Resume Agent 子图
    participant DB as ResumeRepository
    participant CP as LangGraph Checkpoint
    participant EV as ProductEventStore

    U->>F: 打开网页
    F->>API: GET /v1/identity + Cookie
    alt 无有效 Session
        F->>API: POST /v1/identity/guest
        API->>ID: 创建 Principal 与 Session Token 哈希
        API-->>F: Set-Cookie: ia_session(HttpOnly)
    else 已有有效 Session
        API->>ID: Token 哈希认证并得到 principal_id
    end
    F->>API: GET /v1/threads + Cookie
    API->>ID: list_threads(auth.principal)
    U->>F: 上传并指定 Markdown 简历
    F->>API: POST /v1/resumes
    API->>DB: upload(auth.principal.id, Markdown)
    DB-->>F: resume_id + 元数据
    F->>API: PUT /v1/threads/{id}/selected-resume

    U->>F: 发送“优化这份简历”
    F->>API: POST /v1/chat(message, resume_id)
    API->>EV: message.user
    API->>M: SystemMessage(指定简历) + HumanMessage
    M->>DB: 可选 list/search/read_resume
    M->>R: resume_agent(resume_id, user_request?)
    R->>DB: wrapper 按 user_id 校验并读取源简历
    R->>CP: 初始化并持续保存工作草稿

    loop 计划、修改与继续请求
        R-->>API: token / interrupt
        API->>EV: 完整消息、状态、Interrupt 与工作区快照
        API-->>F: SSE event + delta
        U->>F: 审批、建议或新修改请求
        F->>API: POST /v1/chat(resume_value)
        API->>EV: interrupt.resolved
        API->>R: Command(resume=结构化决定)
    end

    alt 保存退出
        R->>DB: 创建新的派生简历
        R-->>M: ToolMessage(结构化结果，不含全文)
        API->>EV: resume.result(saved)
    else 不保存退出
        R-->>M: ToolMessage(discarded)
        API->>EV: resume.result(discarded)
    end
```

## 4. 用户故事一：上传和管理简历

### 用户行为

用户点击聊天框旁的简历按钮，在列表窗口中拖入 `.md` 文件，也可以重命名、删除或选择一份简历。

### 前端数据流

主要入口：

- `frontend/src/ResumePicker.tsx`
- `frontend/src/api.ts`
- `frontend/src/App.tsx`

上传时浏览器读取文件文本，然后发送。JSON 不包含 `principal_id`，身份由同一个请求的 HttpOnly Session Cookie 提供：

```json
POST /v1/resumes
{
  "original_name": "resume.md",
  "content": "# 简历正文"
}
```

FastAPI 先通过 `Depends(current_auth)` 得到可信的 `auth.principal.id`，然后执行：

```python
_resume_repository().upload(
    auth.principal.id,
    req.original_name,
    req.content,
    req.display_name,
)
```

`ResumeRepository.upload` 将这个 ID 写入 `resumes.principal_id`，再返回完整 `ResumeDocument`，其中包含不可变的内部 `id`、原始名称、显示名称和正文。

选择简历时发送：

```json
PUT /v1/threads/{thread_id}/selected-resume
{
  "resume_id": "真实资源 ID"
}
```

该选择是“一次性消息附件”：只随下一条普通用户消息发送。该次流式请求成功完成后，前端把 Thread 的 `selected_resume_id` 清空；请求失败时保留选择以便重试。审批决定、Resume Agent待命阶段的新修改请求和 checkpoint 恢复不会重复携带已消费的简历 ID。

### 后端数据流

接口位于 `src/server/app.py`：

- `POST /v1/resumes`：上传；
- `GET /v1/resumes`：元数据列表；
- `GET /v1/resumes/{resume_id}`：读取正文；
- `PATCH /v1/resumes/{resume_id}`：只修改显示名称；
- `DELETE /v1/resumes/{resume_id}`：删除；
- `GET /v1/resumes/{resume_id}/download`：下载 Markdown；
- `PUT /v1/threads/{thread_id}/selected-resume`：记录当前 Thread 的前端指定项。

资源实现位于 `src/kernel/resumes.py`。`principal_id` 的实际使用点包括：

| 操作 | 隔离方式 |
|---|---|
| `upload` | INSERT 时写入 `principal_id` |
| `create_derived` | 先校验源简历 owner，新记录继承当前 principal |
| `list` | SQL `WHERE principal_id = ?` |
| `require` | 按 ID 查询后使用常量时间比较 owner；不匹配统一按不存在处理 |
| `rename` | 先调用 `require(principal_id, resume_id)` |
| `delete` | 先调用 `require`，删除 Thread 选择关系时也带 principal |
| `search` | 只遍历当前 principal 的 list/require 结果 |
| `read` | 先调用 `require` |

因此不同游客或开发人员之间相互隔离。

简历不会进入知识向量库。`search_resumes` 是对简历正文的独立关键词搜索，不会混入知识库结果。

## 5. 用户故事二：用户明确指定简历并要求修改

### 请求示例

用户在前端选中“0716_agent简历.md”，发送：

> 帮我强化这个项目的多智能体亮点。

### 浏览器到产品层

`frontend/src/api.ts::streamGraph` 发送：

```json
POST /v1/chat
{
  "thread_id": "thread-id",
  "message": "帮我强化这个项目的多智能体亮点。",
  "resume_id": "resume-id",
  "resume_value": null
}
```

后端首先验证 `resume_id` 属于当前用户，然后构造两条图输入消息：

1. `SystemMessage`：包含显示名称与真实 `resume_id`，并声明它只是高优先级上下文；
2. `HumanMessage`：用户原话。

同时写入 `message.user` 产品事件，事件 payload 会附带 `resumeId` 和 `resumeDisplayName`，用于前端在用户消息气泡中显示附件标记。

这里仍然不信任浏览器提供的 owner：服务端用 `auth.principal.id` 调用 `ResumeRepository.require`。若 `resume_id` 属于其他 principal，接口统一返回 404。

### 关于请求模型中遗留的 `user_id`

当前 `ChatRequest` 和 `CheckpointRequest` 仍保留 `user_id="default"` 字段，这是旧接口兼容遗留。当前 React 前端不会发送它，`/v1/chat` 与 `/v1/checkpoint` 也没有用它做授权或 Store 键控；实际图配置始终由服务端写入：

```python
config = {
    "configurable": {
        "thread_id": req.thread_id,
        "user_id": auth.principal.id,
    }
}
```

因此客户端即使伪造请求体 `user_id` 也不能跨用户读取简历。为了减少误解，后续可以删除这两个未使用字段，但这不影响当前隔离有效性。

### 为什么不由后端直接调用 Resume Agent

前端指定不等于后端强制路由。Main Agent仍然可以结合用户最新自然语言判断：

- 用户是否真的要求修改；
- 用户是否在文字中改指另一份简历；
- 是否需要先读取正文；
- 是否应当询问一次入口级澄清。

这一行为由 `src/agents/resume/prompts.py::MAIN_AGENT_GUIDANCE` 提供，并由 Main Agent注册表驱动的静态 Prompt组合器加载。

## 6. 用户故事三：用户没有指定简历，或者请求模糊

### 请求示例 A

> 帮我修改最新的简历。

Main Agent可以调用 `list_resumes`，在没有歧义时优先考虑最近上传的简历。

### 请求示例 B

> 把我简历中的 InterviewAssistant 项目优化一下。

Main Agent可以调用 `search_resumes(query="InterviewAssistant")`，得到命中的 `resume_id` 和行级片段，再按需调用 `read_resume`。

### 请求示例 C

> 帮我优化简历。

如果有多份候选且无法可靠判断，Main Agent应询问用户。若没有任何简历，则提示用户通过聊天框简历入口上传 Markdown。

### Main Agent拥有的最小简历资源工具

实现位于 `src/agents/main/tools/resume_resources.py`：

| 工具 | 输入 | 返回 | 职责 |
|---|---|---|---|
| `list_resumes` | 无 | 元数据列表 | 查有哪些简历，不返回全文 |
| `search_resumes` | query、可选 resume_id | 行级关键词命中 | 按内容缩小候选范围 |
| `read_resume` | resume_id、行区间 | 受控正文 | 读取指定简历内容 |

这些工具都从 `RunnableConfig.configurable.user_id` 获取可信身份，不接受 LLM 自行提供用户 ID。

## 7. Main Agent到 Resume Agent 的交接

入口工具位于 `src/agents/main/tools/resume_agent.py`。

交接 schema 被精简为：

```json
{
  "resume_id": "必填、真实且已验证的资源 ID",
  "user_request": "可选，用户原话或忠实的简短概括"
}
```

不交接以下内容：

- 整份简历正文；
- Main Agent自行生成的完整修改计划；
- 强制填写的岗位、语气、范围等大量字段；
- 用户 ID 或 Thread ID。

`resume_agent_node` wrapper 从可信 `RunnableConfig` 读取 `user_id` 和 `thread_id`，再通过 `ResumeRepository.require(user_id, resume_id)` 验证归属并加载源简历。

wrapper 创建稳定的：

```text
resume_session_id = resume:{principal_id}:{thread_id}:{tool_call_id}
```

该 ID 用于保证 checkpoint 重跑和保存派生简历的幂等性。

如果 `user_request` 为空，Resume Agent以空消息进入，由它结合简历正文询问用户，而不是让 Main Agent为了填满 schema 连续追问。

## 8. Resume Agent图结构与状态流动

实现位于 `src/agents/resume/graph.py`。

```mermaid
flowchart TD
    START --> INIT["init：初始化只读源与工作草稿"]
    INIT --> CHAT["chat_node：唯一 LLM 决策点"]
    CHAT -->|request_plan| PLAN["plan_node"]
    PLAN --> PLAN_CONFIRM["plan_confirm interrupt"]
    PLAN_CONFIRM -->|批准| PLAN_RESULT["plan_result：approved ToolMessage"]
    PLAN_RESULT --> CHAT
    PLAN_CONFIRM -->|建议| PLAN
    CHAT -->|grep_replace| EDIT["edit_executor：定位但不修改"]
    EDIT -->|命中| APPROVE["approve_node：全文 Diff interrupt"]
    EDIT -->|失败/全部完成| CHAT
    APPROVE -->|批准并写入草稿| EDIT
    APPROVE -->|建议| CHAT
    APPROVE -->|拒绝| HITL["hitl_standby interrupt"]
    CHAT -->|无工具调用/总结| HITL
    HITL -->|new_request| CHAT
    HITL -->|保存退出| PERSIST["persist：创建派生简历"]
    HITL -->|不保存退出| END
    PERSIST --> END
```

### 8.1 `init_node`

wrapper 已经读取源简历并传入 `resume_shot`。`init_node` 初始化本次常驻会话需要的草稿、处理记录和输出状态。

### 8.2 `chat_node`

这是 Resume Agent唯一使用 LLM 作业务决策的节点。它看到：

- 当前完整 `resume_shot`；
- 当前计划；
- 用户请求或建议；
- 可选选区提示。

它可以：

- 调用一个或多个 `grep_replace`；
- 调用 `request_plan`；
- 不调用工具并输出总结，进入 `hitl_standby`。

### 8.3 逐条修改审批

一波多个 `grep_replace` 不会一次性全部写入草稿：

1. `edit_executor_node` 取第一个未处理项，只验证目标是否唯一命中；
2. 命中后进入 `approve_node`，构造完整 `before/after` 与局部 `before_text/after_text`；
3. 前端用完整版本做源码原位 Diff 和 Lapis渲染对比；
4. 用户批准后才调用 `_apply_grep_replace` 更新 `resume_shot`；
5. 再处理同一波的下一条修改。

批准后的修改不能逐条撤销，但用户仍可在最后放弃整个草稿。

### 8.4 `hitl_standby`

这是常驻会话的继续入口，不是强制退出节点。

- 用户通过聊天框发送新要求：

```json
{
  "action": "new_request",
  "request": "继续修改技能部分",
  "selection": "可选的工作区选中文本"
}
```

节点注入新的 `HumanMessage`，条件边返回 `chat_node`。

- 保存为新简历并退出：

```json
{"action": "exit", "save": true}
```

- 不保存并退出：

```json
{"action": "exit", "save": false}
```

只有 `hitl_standby` 前端才开放这两个退出按钮；聊天框仍保持可用。

## 9. Interrupt 的前后端协议

业务契约定义在 `src/kernel/contracts.py`。

### 9.1 计划确认

```json
{
  "phase": "plan_confirm",
  "plan": ["步骤一", "步骤二"]
}
```

前端返回 `approve` 或带建议的 `suggest`。

### 9.2 逐条修改审批

```json
{
  "phase": "resume_approve",
  "edit_id": "tool-call-id",
  "ordinal": 1,
  "total": 3,
  "section": "项目经历",
  "reason": "突出多智能体架构",
  "before_text": "局部原文",
  "after_text": "局部候选文本",
  "before": "修改前完整 Markdown",
  "after": "修改后完整 Markdown"
}
```

前端返回 `approve`、`reject` 或 `suggest`。

### 9.3 常驻待命

```json
{
  "phase": "resume_hitl",
  "summary": "本轮修改总结"
}
```

前端返回 `new_request` 或 `exit`。

### 9.4 恢复过程

浏览器把结构化决定放入 `/v1/chat` 的 `resume_value`。服务端检测到 checkpoint 中存在 pending Interrupt 后：

1. 写入 `interrupt.resolved` 产品事件；
2. 校验并规范化 payload；
3. 构造 `Command(resume=value)`；
4. 从准确的子图挂起点继续执行。

预期内的 `interrupt()` 将 Thread 状态记为 `waiting`，前端显示“待确认”，不会显示“上次执行已中断”。只有断线、主动停止或进程异常等非预期暂停才使用 `interrupted`。

## 10. 前端何时读取产品事件，以及如何投影为界面

前端不会在每次渲染或每次发送消息时拉取完整产品事件时间线。当前采用“最新事件分页快照 + 当前请求 SSE 增量”的组合。

### 10.1 打开或切换 Thread

`frontend/src/App.tsx::ChatPage` 监听路由中的 `threadId`。当用户打开页面或切换会话时：

1. 中止前一个 Thread 仍存在的浏览器流；
2. 清空当前内存中的 `events` 和临时 token；
3. 调用 `getEvents(threadId)`；
4. 请求 `GET /v1/threads/{thread_id}/events?limit=50`；
5. 服务端返回该 Thread 最新 50 条事件，并按 `sequence` 从旧到新排列；
6. 前端将这一页直接设为当前时间线。

所以首次打开并不是拉取完整时间线，而是拉取最新一页。

### 10.2 向前加载历史事件

如果服务端返回 `hasMore=true`，时间线顶部显示“加载更早消息”。用户点击后，前端取当前最早事件的 `eventId`：

```text
GET /v1/threads/{thread_id}/events
    ?beforeEventId=<当前最早 eventId>
    &limit=50
```

服务端根据该事件所属的稳定 `sequence` 查询更早一页。前端用 `mergeEvents` 合并，并按 sequence 重新排序。

因此历史记录是按需向前分页，不会随着会话变长而一次性全部传给浏览器。

### 10.3 用户发送消息后的实时增量

用户发送消息后，前端不会轮询事件接口，而是保持 `/v1/chat` 的 SSE 响应连接。

SSE 帧分为：

- `kind="delta"`：尚未持久化的模型 token；
- `kind="event"`：已经形成完整产品事件的记录。

`App.tsx::onFrame` 的处理方式：

1. `delta` 按 `messageId` 累加到 `transient` Map；
2. 页面立即显示带“执行中”状态的临时消息；
3. 服务端在消息边界把完整文本写入 `message.agent`；
4. 前端收到对应 `event` 后加入正式 `events`；
5. 根据相同 `messageId` 删除临时消息，避免重复显示。

正式事件通过 `mergeEvents` 按 `eventId` 去重，再按 `sequence` 排序。这里的去重只防止同一事件帧重复到达，不会把 checkpoint 重跑产生的新事件合并掉，因为重跑事件具有新的 event ID。

一次 SSE 执行结束后，前端调用 `GET /v1/threads` 刷新 Thread 的 `status`、`active_mode` 和 `active_agent`，但不会重新拉取完整事件时间线。

### 10.4 Timeline 如何把事件变成组件

`frontend/src/Timeline.tsx` 是产品事件到聊天界面的主要投影器：

| 产品事件 | 前端展示 |
|---|---|
| `message.user` | 右侧用户头像与消息气泡；可显示本轮指定简历 |
| `message.agent` | 左侧对应 Agent头像和完整消息 |
| `task.*` | 头像右侧的执行中、等待确认、已完成等状态 |
| `agent.transition` | “Main Agent已将任务交给 Resume Agent”等分隔提示 |
| `tool.status` | 可折叠的工具执行卡片 |
| `interrupt.requested` | 当前未解决时显示可操作审批卡；历史事件显示只读审批记录 |
| `interrupt.resolved` | 本身不单独显示；用于判定对应审批已经处理 |
| `resume.result` | 已保存/已放弃结果卡；保存时提供下载入口 |
| `citation.list` | Main Agent回答下方的参考资料卡片 |
| `task.failed/interrupted` | 异常或非预期中断提示 |

`task.status` 不一定独立渲染为一张卡。Timeline 先按 `taskId + source` 汇总最新 label，再把它附加到对应 Agent消息头像右侧。

### 10.5 哪些界面状态不只依赖事件数组

页面布局还使用 `GET /v1/threads` 返回的 Thread 元数据：

- `status`：侧栏显示就绪、执行中、待确认或已中断；
- `active_agent`：聊天框显示当前发送给 Main Agent还是 Resume Agent；
- `active_mode`：决定 Resume 工作区是否常驻；
- `selected_resume_id`：恢复聊天框当前指定的简历。

这意味着前端界面是两类后端数据的组合投影：

```text
Thread 元数据 → 页面布局、当前 Agent、会话状态
产品事件时间线 → 消息、过程卡片、审批历史、工作区展示快照
```

### 10.6 Pending Interrupt 如何推导

`frontend/src/interrupts.ts::pendingInterrupt` 按事件顺序扫描当前已加载事件：

```text
遇到 interrupt.requested → 记为当前 pending
遇到 interrupt.resolved  → 清空 pending
```

最后仍未被 resolved 的 requested 才成为可操作审批卡。历史 requested 永远只读，已审批决定不可再次提交。

Resume 工作区则由以下信息共同决定：

- Thread `active_mode=resume`：决定工作区必须驻留；
- 当前 pending Resume Interrupt：决定是否显示计划、Diff 或待命；
- 最近 Resume Interrupt 的 workspace snapshot：恢复草稿展示；
- `interrupt.resolved` 的批准决定：在下一份快照到达前临时展示候选 `after`。

### 10.7 当前 `afterEventId` 的实际完成度

后端 `ProductEventStore.page` 和前端 `getEvents` 已支持：

```text
afterEventId=<最后已知 eventId>
```

它可以查询该游标之后的新事件。但是当前 React 页面尚未在浏览器断线重连时调用这一能力：

- 正常打开/刷新：重新读取最新 50 条；
- 加载历史：使用 `beforeEventId`；
- 当前执行：依赖 SSE；
- `afterEventId`：接口已具备，当前页面未使用。

因此，“通过 afterEventId 精确续传断线期间产品事件”仍是待完善项，不能视为已经完成。当前刷新恢复通常依靠最新 50 条事件和 Thread 状态；如果未来一次执行可能在断线期间产生超过 50 条事件，应实现 last-event cursor 补齐或专门的状态快照接口。

## 11. 前端工作区如何恢复

主要代码：

- `frontend/src/interrupts.ts`
- `frontend/src/ResumeWorkspace.tsx`
- `frontend/src/App.tsx`
- `frontend/src/Timeline.tsx`

服务端在写入 `interrupt.requested` 时，从 checkpoint 读取只供展示的 workspace snapshot：

```json
{
  "resumeId": "源简历 ID",
  "displayName": "显示名称",
  "draft": "当前工作草稿 Markdown"
}
```

该 snapshot 只写产品事件，不反馈给图。

前端规则：

- `active_mode=resume`：工作区始终驻留；
- pending `resume_approve`：展示完整源码 Diff 和渲染前后对比；
- Interrupt 已解决、下一节点正在执行：继续使用最近快照；批准时临时显示候选 `after`；
- 新快照到达：替换工作区内容；
- `active_mode=chat`：Resume Agent已经保存或放弃退出，工作区关闭。

源码模式在完整 Markdown 原位置插入删除与新增标记。渲染对比中，“修改前”把删除内容标红，“修改后”把新增内容标绿。没有 Diff 时只显示当前草稿。

## 12. 保存与放弃的数据流

### 12.1 保存退出

`persist_node` 调用 `ResumeRepository.create_derived`：

- 不修改源简历；
- 创建新的 `resume_id`；
- 记录 `source_resume_id`；
- 使用稳定 derivation key 保证重复执行不会重复创建；
- 返回 `output_resume_id` 和显示名称。

Resume 子图结束后，wrapper 只向 Main Agent返回最小结构化 `ToolMessage`：

```json
{
  "source_resume_id": "源 ID",
  "output_resume_id": "新 ID",
  "outcome": "saved",
  "summary": "修改总结",
  "display_name": "新简历名称"
}
```

完整草稿不会塞回 Main Agent消息上下文。产品层识别这个 ToolMessage 后写入 `resume.result`，前端展示下载入口。

### 12.2 不保存退出

子图直接结束，不调用 `persist_node`，不会创建新资源。wrapper 返回 `outcome=discarded`，前端时间线显示本轮草稿已放弃。

## 13. Prompt 修改与当前约束

### 13.1 Main Agent Prompt

基础 Prompt与组合器位于 `src/agents/main/prompts.py`。每个子智能体在自己的 `prompts.py` 导出 `MAIN_AGENT_GUIDANCE`，`src/agents/main/registry.py` 只加载实际注册项。

静态组合结果按不可变 Registry 快照缓存，后端进程生命周期内不会在每次 `chat_node` 调用时重算；用户长期 Memory 仍然在每轮动态追加，不进入缓存。

Main Agent基础 Prompt只保留角色、通用真实性原则、优先委托专业能力和遵循工具 schema 等稳定规则。子智能体高层指导负责：

1. 简历是用户级 Markdown 资源，不是 RAG 知识；
2. 只能使用前端上下文或工具返回的真实 `resume_id`；
3. 前端指定是高优先级提示，不是后端强制选择；
4. 未指定时使用 `list_resumes/search_resumes/read_resume`；
5. 多候选无法判断时询问用户；
6. 交接 Resume Agent只传 `resume_id + user_request?`；
7. Main Agent只做入口级澄清，不替 Resume Agent生成详细需求规格或计划。

工具的具体参数、适用时机和限制继续由各 `@tool` 的 description/schema 提供，避免与 System Prompt重复。

### 13.2 Resume Agent Prompt

文件：`src/agents/resume/prompts.py`

当前 Prompt明确：

1. 每轮都注入当前完整工作草稿；
2. `grep_target` 必须从当前草稿原样复制并唯一命中；
3. `section/reason` 用于向用户解释，而不参与替换；
4. 简单修改直接 `grep_replace`；
5. 复杂或不确定时使用 `request_plan`；
6. `request_plan` 由 chat 后的工具路由拦截，不进入普通 ToolNode；
7. 计划建议只写入 `plan_feedback`，不会插入消息历史；
8. 用户通过 `plan_confirm` 批准后，`plan_result` 才用原始 tool_call ID 返回 `status=approved` 的 ToolMessage；
9. `chat_node` 收到 approved 结果后不得再次询问，应立即调用 `grep_replace`；
10. 信息不足时先自然语言询问，不编造经历、岗位或成果；
11. 全部完成后不调用工具，输出总结进入 `hitl_standby`；
12. 已批准修改进入工作草稿且不可逐条回退，但整个草稿仍可放弃。

### 13.3 值得重点人工验证的 Prompt 行为

- “复杂修改必须 request_plan”是否过于刚性，导致不必要的计划确认；
- Main Agent对“最新简历”的判断是否稳定，是否需要更明确的排序说明；
- Resume Agent信息不足时是否真的先询问，而不是臆造修改；
- 一波生成多个 `grep_replace` 时，是否能提供清晰且真实的 `section/reason`；
- 用户拒绝一条后直接进入待命、终止本波剩余修改，是否符合预期；
- 用户在待命阶段继续提要求后，模型能否正确基于已经批准的草稿继续工作；
- 保存完成后的 Main Agent总结是否简洁，是否错误声称覆盖了源简历。
