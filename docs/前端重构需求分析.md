# 前端重构需求分析

> 状态：需求讨论稿
>
> 本文档整理当前已确认的前端产品需求与交互逻辑。现阶段只定义“产品应如何工作”，不决定 React 技术栈、组件实现、接口字段细节或开发阶段拆分。后续在本文档获得认可后，再据此设计重构方案，并反推后端接口与状态模型的改造任务。

## 1. 项目定位

InterviewAssistant 是面向技术学习、面试准备与简历优化的多智能体助手，不是通用聊天机器人，也不是单一的简历编辑器。

产品通过一个连续的会话入口向用户提供三类核心能力：

1. **技术知识问答**：围绕 Agent、LangGraph、AI 工程和面试相关主题回答问题，优先检索本地知识库，并提供文件名与行区间引用。
2. **联网深度研究**：当本地知识不足时，经用户明确同意后制订研究计划、搜索网页、抓取和提炼资料，最终生成带来源的研究结果。
3. **简历优化**：由主 Agent 判断意图并调用 Resume Agent。用户选择本地 Markdown 简历后，Agent 提出计划和逐条修改建议，用户逐条接受、拒绝或补充意见，最终导出修改结果。

产品的整体关系是：

```text
一个连续的面试助手会话
  ├─ 普通知识问答
  ├─ 在会话内启动深度研究
  └─ 在会话内进入简历编辑模式
```

## 2. 产品范围与基本约束

### 2.1 部署与使用方式

- 前端后续将部署上线，用户通过浏览器访问。
- 游客使用自己的模型 API Key。
- 第一版需要多会话与历史会话管理。
- 第一版提供游客模式和开发人员模式，但不实现普通用户注册、登录和账户找回。
- 开发人员模式仅用于本地开发与调试，直接使用服务端 `.env` 中的模型配置，不要求在前端填写 API Key。
- 系统仍需为每个游客建立稳定的本地身份标识，实现多 Thread 会话隔离，以及知识库、配置和未来 Skill 的用户级隔离。
- 第一版简历只支持 Markdown 文件。
- 第一版只支持桌面端，不考虑移动端适配。
- Resume Agent 的 Skill 安装能力属于后续扩展，本轮仅保留概念空间，不纳入首版实现。

### 2.2 交互设计原则

1. 一个历史会话对应一条产品级统一时间线。
2. Agent 可以切换，但聊天内容不刷新、不清空、不跳转到另一套对话记录。
3. Agent 身份对用户可见，但用户不需要手动选择路由。
4. Main Agent 与 Resume Agent 保持独立内部状态，不强行共享完整消息历史。
5. Agent 之间通过结构化交接传递完成任务所需的上下文。
6. 同一时刻，一个会话只有一个接收用户输入的活动 Agent。
7. 中间工作区只服务于简历查看和修改。
8. RAG 引用、工具状态与深研过程均在聊天时间线中呈现。
9. 产品级聊天时间线与 LangGraph 各图的 `messages` 解耦。
10. 刷新或重新进入历史会话后，应恢复产品时间线、活动 Agent、待审批状态和简历工作区。

## 3. 信息架构与页面布局

桌面端采用“左侧会话管理—中间简历工作区—右侧聊天区”的方向，但中间工作区只在 Resume Agent 激活时显示。

### 3.1 普通会话状态

未进入简历编辑模式时，不显示空白工作区。聊天区向左扩展，占据除会话侧栏外的所有可用空间。

```text
┌──────────────────┬──────────────────────────────────────────────┐
│ 会话管理         │                  聊天时间线                  │
│                  │                                              │
│ 新建、搜索       │ 用户消息、Agent 回答、引用、深研过程        │
│ 历史会话         │                                              │
│ 设置             │                                  输入框      │
└──────────────────┴──────────────────────────────────────────────┘
```

### 3.2 简历编辑状态

Resume Agent 激活后，中间展开简历工作区，聊天区保持在最右侧。

```text
┌──────────────────┬────────────────────────────┬─────────────────┐
│ 会话管理         │       简历工作区           │  聊天时间线     │
│                  │                            │                 │
│ 历史会话         │ Markdown / 预览 / Diff     │ 用户与各 Agent  │
│ 待审批标记       │ 当前修改与审批进度         │ 的连续交流      │
│ 设置             │                            │ 输入框          │
└──────────────────┴────────────────────────────┴─────────────────┘
```

### 3.3 区域职责

#### 左侧：会话管理

- 新建会话。
- 搜索历史会话。
- 按日期分组展示历史会话。
- 当前会话高亮。
- 自动生成标题。
- 重命名、删除会话。
- 显示会话的任务类型和待审批状态。
- 进入设置。
- 支持折叠。

#### 中间：简历工作区

- 只在 Resume Agent 激活时出现。
- 展示 Markdown 原文或渲染后的简历预览。
- 显示当前修改的前后 Diff。
- 自动定位当前修改位置。
- 展示修改序号和总数。
- 支持用户选择一段简历文本，作为下一条建议的上下文。
- 提供接受、拒绝、提出建议等与当前修改直接相关的操作。
- 提供最终导出入口。

中间工作区不展示深研进度、RAG 结果、通用工具日志或普通聊天内容。

#### 右侧：统一聊天时间线

- 用户消息。
- Main Agent、Resume Agent 和 Research Agent 的回复。
- Agent 模式切换提示。
- RAG 引用入口。
- 深研计划、关键词、网页 URL 和抓取进度。
- 工具运行状态。
- 计划确认、修改审批等交互卡片。
- 错误、重试、中止和恢复提示。
- 始终保留统一输入框。

## 4. 多 Agent 消息呈现

### 4.1 消息方向

- 用户消息固定显示在右侧。
- 所有 Agent 消息固定显示在左侧。
- 系统状态和模式切换信息居中显示。

### 4.2 Agent 头像与身份

Agent 消息需要同时显示头像、用户可理解的名称和稳定主题色。头像不能作为唯一身份信息。

| 后台角色 | 前端名称 | 视觉概念 | 建议主题色 | 是否作为聊天角色出现 |
|---|---|---|---|---|
| Main Agent | 面试助手 | 对话与调度 | 蓝紫色 | 是 |
| Resume Agent | 简历优化助手 | 文档与笔尖 | 青绿色 | 是 |
| Research Agent | 深研助手 | 搜索与望远镜 | 橙色 | 是 |
| RAG Agent | 不单独命名 | 检索能力 | 跟随发起 Agent | 否 |
| Index Agent | 不单独命名 | 后台索引能力 | 中性状态色 | 否 |
| 系统 | 系统状态 | 信息与流程 | 中性灰 | 仅显示状态 |

RAG Agent 与 Index Agent 属于后台能力，不作为独立聊天角色出现，避免用户面对过多内部技术节点。

### 4.3 连续消息

同一个 Agent 连续输出多条内容时，不必重复显示大头像。出现以下情况时重新显示头像与名称：

- 发言者变化。
- 中间出现用户消息。
- 发生 Agent 模式切换。
- 一段长任务结束并开始新的交互阶段。

### 4.4 模式切换提示

头像回答“谁在说话”，居中的模式分隔条回答“为什么换人了”。

进入 Resume Agent 时：

```text
面试助手 · Main Agent
我会将你的目标整理后交给简历优化助手。

──────── 已进入简历编辑模式 ────────
任务：突出 Agent 项目经验，并保持描述可信

简历优化助手 · Resume Agent
请选择需要优化的 Markdown 简历。
```

退出 Resume Agent 时：

```text
简历优化助手 · Resume Agent
本轮修改已经完成，共接受 5 项、拒绝 1 项。

──────── 已退出简历编辑模式 ────────

面试助手 · Main Agent
简历优化已经完成。接下来要根据这份简历准备面试问题吗？
```

### 4.5 当前输入接收者

输入框附近应显示当前接收者：

```text
发送给：面试助手
```

或：

```text
发送给：简历优化助手
```

用户不手动选择 Agent。接收者由当前会话的活动模式决定。

## 5. 产品级统一时间线

前端展示的完整产品会话不等同于任何一个 Agent 的内部消息历史：

```text
产品级时间线
≠ MainState.messages
≠ ResumeState.messages
≠ ResearchState 内部执行状态
```

### 5.1 时间线内容

产品级时间线至少需要表达：

- 用户消息。
- Agent 消息及其来源。
- Agent 模式切换。
- 流式生成状态。
- 工具调用摘要。
- 深研任务进度。
- Interrupt 与用户决策。
- 错误、重试与中止。
- 任务完成摘要。

### 5.2 时间线与内部状态的关系

- Agent 内部消息历史服务于模型推理。
- 产品时间线服务于用户理解与刷新恢复。
- 前端不应通过简单拼接多个 Agent 的 `messages` 临时构造产品历史。
- 后端需要提供稳定、有序、可恢复的产品事件记录。
- 每个事件需要稳定 ID、来源、类型、所属会话、所属任务和时间信息。

## 6. Main Agent 与 Resume Agent 的上下文交接

### 6.1 不共享完整对话历史

保留 Main Agent 与 Resume Agent 的分离式设计，以维持清晰的职责边界和多智能体架构。Resume Agent 不直接继承 Main Agent 的完整 `messages`。

### 6.2 Main Agent 到 Resume Agent

当前仅传递 `intent` 容易丢失目标岗位、用户偏好和前文约束。后续应扩展为结构化任务交接包，概念上至少包含：

```json
{
  "task": "突出 Agent 项目经验并优化项目描述",
  "original_request": "把刚才聊的项目写进简历，但不要显得夸张",
  "target_role": "后端 Agent 工程师",
  "constraints": [
    "保持一年经验的可信度",
    "强调工程落地",
    "只修改项目经历和技能部分"
  ],
  "relevant_context": [
    "项目使用 LangGraph 多智能体架构",
    "包含 RAG、深研和 HITL 简历优化"
  ]
}
```

该结构只定义产品需求，最终字段在后端方案设计阶段确定。

### 6.3 Resume Agent 到 Main Agent

Resume Agent 退出时，应向 Main Agent 返回结构化结果，例如：

```json
{
  "status": "completed",
  "resume_file": "my_resume.md",
  "accepted_edits": 5,
  "rejected_edits": 1,
  "summary": [
    "重写 Agent 项目描述",
    "补充 RAG 与 HITL 技术点",
    "精简技能列表"
  ],
  "saved": true
}
```

Main Agent 根据该结果恢复对话，向用户总结任务，并自然引导下一步。

## 7. 会话模式与输入路由

产品会话至少包含以下活动模式：

```text
active_mode = main | resume
```

### 7.1 Main 模式

- 用户输入发送给 Main Agent。
- Main Agent 可以调用 RAG Agent。
- Main Agent 可以在用户确认后调用 Research Agent。
- Main Agent 可以根据简历修改意图调用 Resume Agent。

### 7.2 Resume 模式

- Main Agent 暂停在 Resume Agent 调用上。
- 用户输入默认发送给 Resume Agent。
- 中间展开简历工作区。
- 用户可以审批修改、提出建议或继续发起新的简历修改要求。
- 只有用户明确保存退出或放弃退出后，才恢复 Main 模式。

### 7.3 Resume 模式中的无关问题

第一版不让 Main Agent 与 Resume Agent 同时争夺输入框。如果用户在简历编辑过程中提出明显无关的问题，应提示当前正在进行简历编辑，并引导用户先完成或退出当前任务。

“暂停简历任务后临时回到普通问答”可以作为未来能力，不纳入第一版。

## 8. 普通知识问答与 RAG

### 8.1 回答呈现

- Main Agent 流式输出回答。
- 正文保留引用角标。
- 回答下方提供可折叠的参考资料入口。
- 参考资料显示文件名与行区间。
- RAG Agent 不单独显示头像或独立消息。

### 8.2 工具状态

简单、快速的检索不需要展示内部日志，可使用轻量状态，例如：

```text
正在检索知识库…
```

检索完成后状态收起，保留引用结果。

## 9. 深度研究交互

Research Agent 是聊天区中的可见角色，但不会打开中间工作区。

### 9.1 启动条件

- Main Agent 判断本地知识不足。
- Main Agent 先以自然语言询问用户是否启动深研。
- 用户明确同意后，才调用 Research Agent。

### 9.2 计划确认

Research Agent 在聊天时间线中展示研究计划。用户可以批准计划或提出修改建议。

### 9.3 详细进度

研究任务以可展开的进度卡片附属于 Research Agent 消息，至少展示：

- 当前阶段。
- 研究计划。
- 搜索关键词及完成数量。
- 发现的网页 URL。
- 每个 URL 的状态：等待、抓取中、成功、跳过、失败。
- 总体抓取进度。
- 内容提炼进度。
- 报告生成状态。
- 知识库写入或索引状态。

示意：

```text
深度研究 · 进行中

✓ 研究计划
✓ 搜索关键词 3/3
● 抓取网页 4/8
  ✓ docs.langchain.com/...
  ● github.com/...
  ○ blog.langchain.com/...
  × example.com/...  抓取失败
○ 内容提炼
○ 生成报告

[展开详情] [停止研究]
```

### 9.4 完成状态

- 进度卡固定为完成状态。
- Research Agent 提供研究结果摘要和来源。
- Main Agent 根据研究结果给出最终回答。
- Research Agent 在资料整理完成后触发新的 Interrupt，询问用户是否将研究资料加入其个人知识库。
- 用户确认加入后，才执行资料持久化与索引更新；用户拒绝时保留本次研究结果，但不写入个人知识库。
- Interrupt 应明确展示拟写入资料的标题、摘要、来源数量和预期文件名，避免用户在信息不足时确认。

## 10. 简历优化交互

### 10.1 进入流程

1. 用户在普通会话中提出简历优化需求。
2. Main Agent 结合上下文生成任务交接包。
3. Main Agent 调用 Resume Agent。
4. 聊天时间线保留此前消息，并插入“已进入简历编辑模式”。
5. 中间展开简历工作区。
6. Resume Agent 请求用户选择 Markdown 简历。
7. 浏览器读取文件内容并提交给后端。

### 10.2 计划阶段

- 简单修改可以直接进入修改建议。
- 复杂修改由 Resume Agent 先生成计划。
- 计划确认卡片显示在聊天区。
- 用户可以批准计划或提出建议。

### 10.3 逐条修改

第一版暂时保持逐条审批：

1. Resume Agent 提出一条修改。
2. 中间工作区定位对应位置。
3. 工作区显示修改前和修改后。
4. 聊天区显示修改目标、理由和审批卡片。
5. 用户接受、拒绝或提出建议。
6. 系统进入下一条修改。

每条修改至少展示：

- 当前序号和总数。
- 所属章节或位置。
- 修改前内容。
- 修改后内容。
- 修改理由。
- 接受、拒绝和提出建议操作。

### 10.4 隐藏 grep 实现细节

当前后端仍可使用 `grep_target + replace_content` 定位和执行修改，但前端不向用户暴露 grep 概念。前端统一表达为：

```text
定位区域 + 修改前 + 修改后 + 修改理由
```

这样后续后端改用 Markdown AST、块 ID、段落锚点或结构化编辑操作时，前端交互模型无需推倒重来。

### 10.5 常驻编辑会话

完成一轮修改后，Resume Agent 进入待命状态。用户可以：

- 继续提出新的修改要求。
- 根据简历选区提出要求。
- 导出并结束。
- 放弃修改并结束。

### 10.6 退出流程

1. Resume Agent 展示本轮修改总结。
2. 用户明确选择保存退出或放弃退出。
3. 保存时由浏览器导出最终 Markdown。
4. 中间工作区关闭。
5. 时间线插入“已退出简历编辑模式”。
6. Resume Agent 把结构化结果交回 Main Agent。
7. Main Agent 恢复对话并引导下一步。

### 10.7 审批不可撤销

第一版中，已经接受或拒绝的修改不可撤销。用户如需调整已经处理的内容，应在后续对话中提出新的修改要求，由 Resume Agent 生成新的修改建议。

## 11. 会话管理与恢复

### 11.1 会话列表

每个会话建议保存并展示：

- 标题。
- 创建时间和更新时间。
- 最近消息摘要。
- 当前任务类型。
- 当前活动 Agent。
- 是否存在待审批操作。
- 当前使用的模型配置标识。

### 11.2 刷新恢复

刷新页面或重新进入历史会话后，应恢复：

- 完整产品时间线。
- 当前活动 Agent。
- 当前输入接收者。
- 当前执行阶段。
- Pending interrupt。
- 简历内容与文件名。
- 当前 Diff。
- 修改进度。
- 深研进度或最终状态。

### 11.3 会话切换

用户切换会话或离开当前页面时，正在运行的 Agent 任务应自动中断，并由 checkpointer 保存最近可恢复检查点。重新进入会话后，前端自动检测未完成状态，并从最近检查点继续执行。

第一版不允许多个历史会话同时运行长任务。一个游客在同一时刻最多有一个正在执行的长任务；切换会话前必须中断当前执行。这里的“自动中断”需要区分可安全暂停的图节点边界与正在进行的外部网络请求，具体取消和恢复语义在后端方案阶段确定。

恢复语义以 LangGraph checkpoint 和超级步为边界：中断时未完成的单个节点，或者同一未完成超级步中的多个节点，可以在恢复后整体重新执行。产品不承诺从节点内部继续，也不把重复搜索、抓取等视为恢复失败。涉及文件写入、索引和删除等操作时，应保证超级步重新执行后的最终结果一致。

### 11.4 开发人员模式

开发人员模式用于本地调试 LangGraph 图和 React/FastAPI 交互，不属于面向公网用户的完整账户系统。

- LangGraph Studio 直接加载 `langgraph.json` 与服务端 `.env`，不依赖前端或浏览器 API Key。
- 通过 React 页面联调时，可以进入开发人员模式，由后端使用 `.env` 中的 provider、Base URL、模型名和 API Key。
- 开发人员的 Thread、事件、知识库和未来 Skill 使用独立开发作用域，不与游客数据混合。
- 前端不能读取或显示 `.env` 中的 API Key，只显示“正在使用开发环境配置”等非敏感状态。
- 开发人员模式必须由服务端配置显式开启，不能仅由客户端请求参数决定。
- 生产部署默认关闭开发人员模式；若需在非本机环境开启，必须增加独立访问凭证和网络访问限制。
- 开发人员模式不得成为游客绕过自带 API Key 的入口。

## 12. API Key 与模型配置

### 12.1 设置内容

设置页至少需要：

- 服务商预设。
- OpenAI Compatible Base URL。
- 模型名。
- API Key。
- 测试连接。
- 默认模型配置。
- 是否在当前设备记住配置。

开发人员模式不要求填写 API Key，只读显示当前采用“开发环境配置”，且不得返回 `.env` 的实际密钥值。

### 12.2 安全要求

- API Key 不进入聊天消息。
- API Key 不进入 LangGraph checkpoint。
- API Key 不写入日志。
- API Key 不通过 URL 传递。
- 错误信息不得回显完整 API Key。
- 前端不得把 Key 意外发送给不相关的第三方服务。
- 后端不得把用户 API Key持久化到数据库、文件、checkpoint、Store 或日志。
- 网络传输必须使用 HTTPS/WSS，禁止通过明文 HTTP 传输 API Key 或任何可还原的密钥材料。
- 服务端应按身份模式隔离运行时模型凭据：游客使用其请求提交的配置；只有服务端确认的开发人员会话和 LangGraph Studio 才使用 `.env`。

### 12.3 Cookie 的安全边界

不建议直接把 API Key 存入普通 Cookie：

- 普通 Cookie 会随匹配域名的请求自动发送，增加意外泄漏面。
- `HttpOnly` Cookie 虽能降低前端脚本窃取风险，但仍会被发送到后端，而且前端无法读取它来直接调用模型服务。
- 非 `HttpOnly` Cookie 可被 JavaScript 读取，其安全性不优于 Web Storage，并存在 XSS 窃取风险。
- Cookie 的 `Secure` 属性只能保证通过 HTTPS 发送，不能做到“后端永远看不到 Key”。

当前 LangGraph 和 LLM 调用运行在后端，因此只要继续由后端调用模型，API Key 就必然需要在请求运行期间到达后端内存。HTTPS 可以保证不明文传输，但无法让后端进程完全看不到 Key。前端加密后再由同一后端解密，也不能改变这一信任边界。

若要求 API Key 永不进入后端，只能把模型调用迁移到浏览器或引入用户控制的独立代理；这会与当前后端 LangGraph 编排、工具调用和 checkpoint 架构产生根本冲突，不作为第一版默认方向。

### 12.4 第一版建议策略

在“不持久化到后端”和“继续由后端执行 LangGraph”的约束下，第一版建议：

1. API Key 只保存在用户设备的浏览器会话存储中，关闭会话后自动清除。
2. 不使用 Cookie 自动携带 API Key。
3. 前端仅在需要启动或恢复 Agent 执行时，通过 HTTPS 请求头提交 Key。
4. 后端只在该次请求或受控的短生命周期执行上下文中使用 Key，不落盘、不写日志、不进入 checkpoint。
5. 如果 SSE 请求结束而图处于 Interrupt，恢复时由前端重新提交 Key。
6. 可选的“在此设备记住”功能暂不作为默认能力；若后续加入，应使用 Web Crypto 基于用户口令加密后存入 IndexedDB，并明确说明这只能降低静态读取风险，不能防御页面运行时的 XSS。

最终采用请求级提交还是短生命周期内存会话，需要在技术方案阶段通过原型验证 LangGraph 长任务、Interrupt 恢复和断线重连场景。

### 12.5 凭据来源规则

后端根据服务端已经确认的身份模式选择凭据来源，客户端不能任意指定或切换：

```text
游客会话          → 仅使用当前请求安全提交的游客模型配置
开发人员会话      → 仅使用服务端 .env 开发配置
LangGraph Studio  → 直接使用服务端 .env 开发配置
```

游客请求缺少 API Key 时必须阻止模型执行，不能静默回退到服务端 `.env`。

## 13. 知识库管理

知识库管理指向用户提供以下能力：

- 上传自己的 Markdown 资料。
- 查看已导入文件。
- 查看索引状态。
- 删除或重新索引文件。
- 查看深研产生的资料。
- 区分系统资料和个人资料。

知识库管理正式纳入本轮重构范围。除了页面能力，还必须支持用户级数据隔离：

- 每个游客只能查看和操作自己的个人知识库。
- 系统公共知识库与游客个人知识库必须明确区分。
- 深研资料只有在用户确认 Interrupt 后才能进入当前游客的个人知识库。
- 上传、删除、重建索引和检索均需携带稳定的游客身份，并校验资源归属。
- Chroma collection、metadata、文件目录和索引文件的隔离方式在后端方案阶段确定。
- 隔离模型还需兼容未来 Skill 的用户级安装和启用，但本轮不实现 Skill 安装功能。

## 14. Resume Skill 后续扩展

   └─ 简历写作规范  已启用

## 15. 典型用户故事

### 15.1 普通知识问答

用户新建会话，询问 LangGraph 子图状态问题。Main Agent 检索本地知识库并流式回答，在回答下方提供可展开的文件与行区间引用。页面保持普通双栏布局。

### 15.2 启动深研

用户询问知识库中没有的问题。Main Agent 说明资料不足并询问是否深研。用户确认后，Research Agent 在聊天区展示计划。计划获批后，同一张任务卡实时更新关键词、网页 URL、抓取进度、失败状态、提炼进度与报告状态。研究完成后，Research Agent 通过 Interrupt 询问是否加入个人知识库；只有用户确认后才写入并索引。整个过程不打开中间工作区。

### 15.3 从普通对话进入简历优化

用户先告诉 Main Agent 自己准备投递后端 Agent 工程师、经验较少且不希望描述过于夸张，然后要求把刚才讨论的多智能体项目写进简历。

Main Agent 从前文提取目标岗位、表达约束和相关项目内容，生成结构化交接包并调用 Resume Agent。聊天记录不清空，时间线插入模式分隔条，中间展开简历工作区。Resume Agent 因获得必要上下文，不会表现得像突然失忆。

### 15.4 逐条审批简历修改

用户选择 Markdown 简历。Resume Agent 提出第一条修改，中间工作区自动定位并显示 Diff，聊天区说明理由。用户接受后进入下一条；如果用户不满意，可以直接告诉 Resume Agent 如何调整。直到本轮修改全部处理完毕。

### 15.5 结束简历任务

Resume Agent 汇总接受和拒绝的修改。用户选择导出并结束，浏览器导出 Markdown，中间工作区关闭。时间线插入退出分隔条，Main Agent 收到结构化结果并继续询问用户是否需要根据简历准备面试问题。

### 15.6 刷新与历史恢复

用户在第 3/7 条修改审批时刷新页面。系统恢复统一时间线、Resume Agent 身份、中间简历、当前 Diff 和审批卡片。输入框仍显示“发送给：简历优化助手”。切换到其他会话再返回时，也保持相同状态。

## 16. 从前端需求反推的后端缺口

本节只记录能力缺口，不在本文档中确定实现方案。

### 16.1 必须新增或重构

- 多会话创建、列表、读取、重命名与删除。
- 稳定的游客身份，以及游客间 Thread、知识库、模型配置和未来 Skill 的数据隔离。
- 产品级统一事件时间线。
- 稳定事件 ID、来源、类型、顺序、时间和任务归属。
- 会话当前活动模式与活动 Agent。
- Main Agent 到 Resume Agent 的结构化任务交接。
- Resume Agent 到 Main Agent 的结构化任务结果。
- Resume 工作区所需的可恢复展示状态。
- Research Agent 的细粒度计划、搜索、URL、抓取、提炼和索引进度事件。
- Research Agent 完成后的“是否加入个人知识库”Interrupt。
- 停止生成与停止深研。
- 切换会话或离开页面时自动中断，以及重新进入后从最近 checkpoint 自动恢复。
- 单游客同一时刻只允许运行一个长任务的互斥控制。
- 请求并发、重复点击和重复恢复保护。
- 用户提供的 API Key 与模型配置注入。
- API Key 的隔离、脱敏和安全存储策略。
- 个人知识库上传、列表、删除、索引状态、重建和资源归属校验。

### 16.2 已有但需要演进

- SSE 已支持 `ns` 区分 Main Agent 与 Resume Agent，可演进为稳定的 Agent 来源字段。
- `/v1/state` 已能读取主图和 Resume 子图部分状态，但尚不能恢复完整产品时间线。
- Resume interrupt 已具备文件选择、计划确认、逐条 Diff、审批和待命协议。
- Main Agent 已向 Resume Agent 传递 `intent`，但上下文交接信息不足。
- Resume Agent 已向主图返回总结和最终简历，但结果结构不够完整。
- 当前进程级单 `thread_id` 不满足上线后的多会话与多用户需求。
- 当前模型配置统一依赖服务端全局 `.env`；后续需改为游客运行时配置与受控开发 `.env` 配置双路径。

## 17. 已确认决策与剩余安全问题

### 17.1 已确认决策

1. 深研完成后新增 Interrupt，由用户确认是否加入个人知识库。
2. 知识库管理纳入本轮正式重构范围。
3. 本轮设计多 Thread 会话隔离，以及多游客的知识库隔离，并为未来 Skill 隔离预留一致的身份边界。
4. 第一版提供游客模式和开发人员模式，不实现普通用户注册登录；游客使用自己的 API Key，开发人员与 LangGraph Studio 使用服务端 `.env` 配置。
5. Resume 已审批决定不可撤销。
6. 离开或切换会话时自动中断；再次进入时从 checkpointer 最近检查点自动恢复。
7. 第一版不允许多个历史会话同时运行长任务。
8. 第一版不考虑移动端。
9. 开发人员模式仅用于受控开发环境，生产默认关闭，不能由客户端自行声明或借此使用服务端密钥。

### 17.2 API Key 仍需通过原型验证的事项

产品安全目标已经明确：API Key 不在后端持久化、不进入日志或 checkpoint、不通过明文网络传输。由于后端负责运行 LangGraph 和调用模型，Key 在执行期间仍必须到达后端内存。

技术方案阶段需要重点验证：

- 请求级提交 Key 能否覆盖长时间 SSE 执行。
- Interrupt 后恢复时如何安全地重新提交 Key。
- 页面刷新和自动恢复时，浏览器会话存储中的 Key 是否仍可用。
- 后端如何保证异常、追踪和第三方库日志不记录请求头或 Key。
- 游客身份与 API Key 不绑定持久化时，如何避免串用运行时凭据。
