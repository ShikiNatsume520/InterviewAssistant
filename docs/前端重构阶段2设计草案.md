# 前端重构阶段 2：统一产品事件时间线设计草案

> 状态：边界已陈述，快速原型已通过，等待协商
>
> 本阶段只建立产品事件与统一时间线协议，不创建 React 正式工程，不提前实现 Resume 工作区、Research 详细进度、知识库或 API Key 注入。

## 1. 阶段边界

### 本阶段实现

- 与 LangGraph `messages` 解耦的产品事件表。
- Thread 内严格递增的事件顺序。
- 稳定事件 ID 与历史游标分页。
- 统一 SSE 传输 envelope。
- 用户、Main Agent、Resume Agent、Research Agent 和系统来源映射。
- 用户消息、Agent 消息、模式切换、工具状态、Interrupt、完成、失败、取消事件。
- 刷新、断线重连和重复事件去重规则。
- 旧 checkpoint 没有产品事件时的明确兼容行为。

### 本阶段不实现

- React 正式页面及前端工程选型。
- Main 与 Resume 的结构化交接内容。
- Resume 中间工作区和 Diff 审批组件。
- Research 节点拆分及 URL 级进度。
- 知识库事件和知识库页面。
- 游客运行时 API Key。
- 主动停止接口；本阶段只记录现有 SSE 断连导致的取消结果。
- 修改 LangGraph 的节点、边、State、Prompt 或业务执行逻辑。

### 增量接入位置

本阶段只在 LangGraph 外围增加事件投影：

```text
HTTP 请求
  → Event Adapter 先记录用户消息和 task.started
  → 原样调用现有 graph.astream / checkpoint 恢复
  → Event Adapter 观察 namespace、Message、ToolMessage 和最终状态
  → 写入可展示事件并通过 SSE 输出
```

事件适配器只能观察图输出，不能把事件查询结果塞回图配置或 State。当前流中无法可靠观察到的业务细节留到对应功能阶段设计，不能为了填满时间线而猜测事件。

## 2. 快速原型结论

### 2.1 事件存储探针

原型：[frontend_phase2_event_timeline_probe.py](../prototypes/frontend_phase2_event_timeline_probe.py)

已验证：

- 并发追加时可以为每个 Thread 产生连续且无重复的 `sequence`。
- `event_id` 保持稳定，React reducer 可以用它去重。
- `afterEventId` 能精确恢复该事件之后的时间线。
- 其他 Thread 的游标会被拒绝，不能用游标绕过 Thread 所有权。
- 事件数据可以与 API Key 字段完全隔离。
- Windows 下 SQLite 原型必须在清理临时目录前显式关闭连接。

### 2.2 时间线视觉原型

原型：[frontend-phase2-timeline.html](../prototypes/frontend-phase2-timeline.html)

原型表达：

- 用户消息固定在右侧。
- Main、Resume、Research 消息固定在左侧，使用不同头像与名称。
- Agent 切换使用时间线分隔条，不清空聊天区。
- 工具调用和进度使用卡片，不占用 Resume 工作区。
- 恢复游标属于数据层状态，不作为普通聊天气泡反复展示；原型顶部文字只用于说明验证结果。

## 3. 两层协议

产品事件和 SSE 传输帧需要分开定义。

### 3.0 产品事件与图执行的硬边界

产品事件只用于前端展示，是 LangGraph 执行过程产生的只读投影：

- LangGraph checkpoint 是图恢复和继续执行的唯一依据。
- 产品事件绝不作为图输入，不参与节点路由、业务判断、Interrupt 恢复或 checkpoint 选择。
- 事件写入失败可以影响前端可观察性，但不能改变图的状态转移语义。
- 从 checkpoint 重跑未完成超级步时，允许再次产生语义相同的产品事件。
- 重跑产生的是新的真实执行记录，应分配新 `eventId` 并在时间线中再次展示。
- 只有 SSE/历史接口重复传输了同一条已持久事件时，前端才按相同 `eventId` 去重。

因此，时间线出现“步骤 A → 意外中断 → 步骤 A → 继续执行”是允许且真实的，不尝试用产品事件推断哪些图节点应跳过。

### 3.1 持久产品事件

持久事件用于历史、刷新恢复和跨设备内同一游客会话恢复：

```json
{
  "eventId": "opaque-stable-id",
  "threadId": "thread-id",
  "sequence": 23,
  "taskId": "task-id-or-null",
  "type": "message.agent",
  "source": "resume",
  "occurredAt": "2026-07-15T10:33:00Z",
  "payload": {}
}
```

约束：

- `eventId` 全局唯一且不表达资源归属。
- `sequence` 只在单个 Thread 内严格递增。
- 事件只追加，不原地修改。
- `payload` 按事件类型校验。
- 不保存 API Key、请求头、模型密钥、完整异常堆栈或敏感调试信息。

### 3.2 SSE 传输帧

SSE 连接中存在三类帧：

```text
event      已持久化的产品事件，包含完整 ProductEvent
delta      临时 token 增量，引用 messageId，不逐条持久化
heartbeat  保持连接，不进入产品时间线
```

`delta` 不是产品事件，不分配 `eventId`，也不参与 `afterEventId`。前端把它追加到当前临时消息；收到终态 `message.agent` 后，用持久化正文替换临时内容。

如果 SSE 断开：

1. 后端取消本轮执行。
2. 未形成完整产品消息的 token chunk 不持久化，允许丢失。
3. 追加 `task.interrupted`，前端把头像旁状态替换为“已中断”。
4. 前端重新进入 Thread 时从历史接口恢复到最后一个完整产品事件；下次从 checkpoint 重跑产生的新事件继续追加在中断事件之后。

## 4. 事件顺序与并发

事件排序只使用服务端 `sequence`，不使用客户端时间，也不使用 `occurredAt` 排序。

追加事件时，在同一数据库事务中：

1. 校验 Thread owner。
2. 获取该 Thread 的下一个 sequence。
3. 插入事件。
4. 提交后才向 SSE 发送 `event` 帧。

因此客户端看到 durable event 时，该事件已经能从历史接口读取。不同 Thread 的 sequence 互不影响。

## 5. 历史读取与恢复

建议接口：

```text
GET /v1/threads/{threadId}/events?afterEventId=...&limit=...
GET /v1/threads/{threadId}/events?beforeEventId=...&limit=...
```

- `afterEventId`：SSE 断线或页面恢复时向后补齐。
- `beforeEventId`：用户向上滚动时加载更早历史。
- 不传游标：首次打开 Thread 时返回最新一页，并保持升序展示。
- 两个参数不能同时提交。
- 游标不存在或不属于当前 Thread 时返回 400；Thread 不属于当前身份时仍返回 404。
- 返回值包含 `events`、`hasMore`，不把数据库 sequence 直接当作授权凭据。

前端 reducer：

1. 按 `eventId` 去重。
2. 按 `sequence` 排序。
3. 同一个 `messageId` 的 transient delta 只存在内存。
4. 收到终态消息后丢弃对应 transient buffer。

## 6. 第一版事件类型

| 类型 | 来源 | 前端用途 |
|---|---|---|
| `message.user` | `user` | 右侧用户气泡 |
| `message.agent` | `main/resume/research` | 左侧 Agent 气泡；包含完成、取消或失败的正文状态 |
| `agent.transition` | `system` | Agent 切换分隔条 |
| `tool.status` | Agent | 可折叠工具状态卡；只保存产品可理解信息 |
| `interrupt.requested` | Agent | 可操作确认卡 |
| `interrupt.resolved` | `user` | 已完成且不可再次操作的决定记录 |
| `task.started` | Agent | 创建头像旁“执行中”状态 |
| `task.status` | Agent | 用更具体的完整状态替换当前动态提示 |
| `task.completed` | Agent | 头像旁任务完成状态 |
| `task.failed` | Agent | 头像旁脱敏错误和可重试提示 |
| `task.interrupted` | Agent | 头像旁断连/停止后的中断状态 |

阶段 2 不提前增加 `research.plan/source/progress` 和 `resume.diff` 的正式 payload；等对应阶段明确真实交互后再加入。

## 7. Agent 来源规则

```text
空 namespace                         → main
resume_agent:<namespace-id>         → resume
research_agent:<namespace-id>       → research
用户提交                            → user
任务生命周期与模式分隔              → system
```

RAG 和 Index 第一版不显示独立 Agent 头像：

- RAG 作为调用它的可见 Agent 的工具状态展示。
- Index 是后台能力，不进入聊天时间线；未来知识库页面单独展示索引任务。

未知 namespace 不静默映射成 Main。后端记录脱敏诊断，产品事件使用 `system` 或拒绝生成错误来源事件。

## 8. 消息生命周期

一次普通回复建议产生：

```text
message.user（持久）
task.started（持久，头像旁显示“执行中”）
task.status（按需持久，例如“正在调用工具”）
delta × N（仅 SSE）
message.agent（持久，完整正文）
task.completed（持久，头像旁替换为“已完成”）
```

为了让 `message.agent` 在开始流式输出前就有稳定引用，SSE `delta` 使用独立 `messageId`；只有正常形成完整消息时才追加使用同一 `messageId` 的 `message.agent`。中断时前端丢弃该 transient buffer。

前端按照 `taskId + source` 对任务状态做展示投影：最新状态替换头像右侧的当前提示，但数据库事件仍全部追加保留。短任务也必须显示状态；长任务可在状态下方增加更丰富的任务卡片。

## 9. Interrupt 幂等

- `interrupt.requested` 保存稳定 `interruptId`、phase 和展示 payload。
- 用户恢复请求必须提交 `interruptId`。
- 第一次有效决定追加 `interrupt.resolved`，并启动图恢复。
- 同一个 `interruptId` 再次提交时不重复恢复图，返回此前决定或冲突结果。
- 已审批决定不可撤销。

LangGraph 原始 Interrupt payload 仍属于 Agent 执行状态；产品事件保存经过白名单转换的可展示副本。

## 10. 旧 checkpoint 兼容建议

阶段 2 上线前已经存在的旧 Thread 只有 LangGraph messages，从未写入产品事件，因此缺少产品时间线顺序，尤其无法还原 Main 与 Resume 消息的真实交错顺序。阶段 2 上线后产生的产品事件顺序是确定的，刷新时严格按其 `sequence` 原样恢复。

建议不伪造迁移历史：

1. 首次读取旧 Thread 时追加一条 `system.legacy_notice`（也可归入 `tool.status`，待命名确认）。
2. 提示“此会话创建于时间线升级前，旧消息无法完整还原；Agent 执行状态仍可继续”。
3. 从用户下一次提交开始记录完整产品事件。
4. `/v1/state` 在过渡期继续供旧静态前端使用，React 时间线不再用它拼聊天历史。

这样不会把缺少时间戳和跨 Agent 顺序的信息伪装成可靠历史。
