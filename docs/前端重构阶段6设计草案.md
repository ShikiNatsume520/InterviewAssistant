# 前端重构阶段 6 设计草案：Research 详细进度与知识库确认

> 状态：边界已确认，正式实现中。
>
> 本阶段仍遵循：LangGraph checkpoint 是执行真相；产品事件只用于前端展示，图不得读取产品事件。

## 1. 阶段目标

把 Research Agent 从“确认计划后长时间无反馈、完成后直接写入全局知识库”的后台流程，重构为可理解、可观察、可中断的研究任务：

1. 在聊天时间线中显示 Research Agent 身份；
2. 展示计划、检索词、URL、抓取、提炼和报告生成进度；
3. 单个来源失败不隐瞒，并显示可理解的失败状态；
4. 报告完成后通过 Interrupt 询问是否加入个人知识库；
5. 用户拒绝时绝不写文件、索引或向量库；
6. Research 流程不打开 Resume 中间工作区。

## 2. 当前实现审计

当前 Research 图为：

```text
outline
  → outline_confirm interrupt
  → connectivity_check / connectivity_interrupt
  → search
  → finalize
  → index_rebuild
  → END
```

主要问题：

- `search_node` 一次性遍历全部关键词和 URL，并在节点内部完成搜索、抓取和 LLM 提炼；期间没有可供产品层观察的结构化状态更新；
- `finalize_node` 生成报告后立即写入全局 `MARKDOWN_DIR`；
- `index_rebuild_node` 无条件跨子图调用 Index Agent；
- 没有“是否加入个人知识库”的 Interrupt；
- `ResearchState` 只保存最终笔记，没有 URL 级状态、失败原因、总体进度和待入库报告；
- wrapper 默认告诉 Main Agent“已写入知识库并重建索引”，无法表达仅完成研究、拒绝入库或等待入库；
- 前端对未知 Interrupt 的兜底会错误渲染成 Resume Agent 待命卡；
- 当前 SSE 只消费 `messages`，没有把 Research 子图状态更新转换为产品事件。

## 3. 本阶段边界

### 3.1 正式范围

#### Research 图

- 拆分 URL 发现、单页抓取、单页提炼和报告生成；
- 为当前关键词、当前 URL、来源状态、计数和报告产物建立正式状态；
- 报告生成与知识库写入决策分离；
- 新增知识库确认 Interrupt；
- 删除确认前写 `MARKDOWN_DIR` 和无条件调用 Index Agent 的行为；
- 返回结构化研究结果、来源、报告和知识库决策状态。

#### 产品事件适配

- 服务端同时观察 `messages` 与嵌套子图 `updates`；
- 只把完整的节点更新转换成产品事件，不持久化 token chunk；
- 产品事件写入失败不影响图执行；
- 图不读取产品事件，也不根据产品事件决定恢复位置。

#### React 前端

- Research Agent 头像与任务状态；
- 计划确认和网络重试卡片；
- 一张可折叠的研究进度卡；
- URL 状态、总体计数、失败原因和报告状态；
- 知识库确认卡片；
- 停止按钮通过取消当前 SSE 任务触发已有中断语义；
- 刷新后从产品事件时间线恢复任务卡展示。

### 3.2 不进入本阶段

- 不实现知识库管理页面；
- 不实现 Markdown 上传、删除、重新索引；
- 不实现公共库与个人库的最终目录、collection 和 Retriever 隔离；
- 不让 RAG 查询尚未正式导入的研究产物；
- 不实现来源失败后的单 URL 手动重试；
- 不实现多个并行 Research 任务；
- 不实现移动端；
- 不把产品事件改造成图输入。

## 4. 建议图结构

```text
START
  → outline
  → outline_confirm interrupt
      ├─ suggest → outline
      ├─ reject  → abort
      └─ approve → connectivity_check
  → connectivity_interrupt（按现有规则重试）
  → discover_query
  → prepare_source
  → fetch_source
      ├─ failed  → advance_source
      └─ fetched → prepare_distill
  → distill_source
  → advance_source
      ├─ 仍有 URL   → prepare_source
      ├─ 仍有关键词 → discover_query
      └─ 全部完成   → compose_report
  → knowledge_confirm interrupt
      ├─ approve → mark_import_accepted
      └─ reject  → mark_import_rejected
  → END
```

`prepare_source` 与 `prepare_distill` 是有实际展示价值的状态节点：前者在耗时抓取前把 URL 标为“抓取中”，后者在 LLM 提炼前标为“提炼中”。服务端收到这些完整更新后即可立即刷新任务卡。

## 5. ResearchState 草案

```python
class ResearchSource(TypedDict):
    source_id: str
    query: str
    url: str
    title: str
    status: Literal[
        "pending",
        "fetching",
        "fetched",
        "distilling",
        "succeeded",
        "failed",
        "skipped",
    ]
    failure_reason: str
    note: str


class ResearchState(TypedDict, total=False):
    gap_topic: str
    outline: list[str]
    query_cursor: int
    source_cursor: int
    sources: list[ResearchSource]
    current_raw_content: str
    phase: Literal[
        "planning",
        "waiting_plan",
        "checking_network",
        "searching",
        "fetching",
        "distilling",
        "composing_report",
        "waiting_knowledge_decision",
        "completed",
        "aborted",
    ]
    report_markdown: str
    report_summary: str
    proposed_file_name: str
    knowledge_decision: Literal["pending", "accepted", "rejected"]
    approval_status: Literal["approved", "rejected", "aborted"]
```

约束：

- `source_id` 在 URL 被发现时生成，后续所有状态更新复用；
- `sources` 是图的执行状态，不是产品事件；
- 原始网页正文只暂存在 `current_raw_content`，提炼完成后清空，避免 checkpoint 长期保存全部网页；
- `report_markdown` 是研究产物，不等于已经进入知识库；
- 来源失败时记录受控、脱敏后的原因，不把异常堆栈暴露给前端。

## 6. 产品事件草案

建议新增以下事件：

```text
research.plan
research.progress
research.source
research.report
research.knowledge-decision
```

### `research.plan`

```json
{
  "topic": "LangGraph 时间旅行",
  "keywords": ["...", "..."],
  "status": "waiting|approved|replanning"
}
```

### `research.progress`

```json
{
  "phase": "fetching",
  "label": "正在抓取网页",
  "queriesCompleted": 1,
  "queriesTotal": 3,
  "sourcesCompleted": 2,
  "sourcesTotal": 6
}
```

### `research.source`

```json
{
  "sourceId": "stable-id",
  "query": "checkpoint replay",
  "url": "https://example.com/page",
  "title": "Page title",
  "status": "fetching|distilling|succeeded|failed|skipped",
  "failureReason": ""
}
```

### `research.report`

```json
{
  "status": "ready",
  "topic": "LangGraph 时间旅行",
  "summary": "...",
  "sourceCount": 5,
  "proposedFileName": "deep_research_xxx.md"
}
```

### `research.knowledge-decision`

```json
{
  "decision": "accepted|rejected",
  "importStatus": "not_started"
}
```

所有事件均携带现有 `taskId`、稳定 `eventId`、Thread 顺序和 `source=research`。前端按 `taskId` 聚合成一张任务卡，并按 `sourceId` 覆盖同一 URL 的展示状态；数据库仍保持事件只追加。

## 7. Interrupt 契约

### 7.1 计划确认

继续使用 `outline_confirm`，前端补齐专用展示和批准、调整、拒绝操作。

### 7.2 网络重试

继续使用 `connectivity_check`，显示失败次数和继续按钮。它属于预期 Interrupt，不显示“意外中断”提示。

### 7.3 知识库确认

```python
class ResearchKnowledgeConfirmPayload(BaseModel):
    phase: Literal["research_knowledge_confirm"]
    topic: str
    title: str
    summary: str
    source_count: int
    proposed_file_name: str


class ResearchKnowledgeDecisionInbound(BaseModel):
    action: Literal["approve", "reject"]
```

该 Interrupt 只询问是否允许导入，不把报告正文重复塞入产品事件。

## 8. 前端投影逻辑

前端不从 checkpoint 构造历史聊天内容，只从产品事件投影：

1. 收到 `agent.transition → research` 后显示 Research Agent；
2. `research.plan` 创建或更新计划区域；
3. `research.progress` 更新阶段标题与总进度；
4. `research.source` 按 `sourceId` 更新 URL 行；
5. `research.report` 展示研究完成摘要；
6. `interrupt.requested` 的 phase 为 `research_knowledge_confirm` 时显示确认按钮；
7. `interrupt.resolved` 后卡片变为历史只读状态；
8. `research.knowledge-decision` 显示用户选择；
9. 刷新或分页加载时，按事件顺序重新执行同一投影。

研究卡位于聊天区，不触发中间工作区。URL 列表默认折叠，当前正在处理和失败来源保持可见。

## 9. 停止与恢复

- 用户点击“停止研究”时取消当前前端 SSE 请求；
- 服务端沿用现有任务生命周期，把非预期结束记录为 `task.interrupted`；
- LangGraph 从最近可用 checkpoint 恢复，允许未完成节点或子图超级步重跑；
- 产品事件不会回滚，恢复后允许出现重复的关键词、URL 或来源状态事件；
- 前端按事件顺序如实展示，稳定 `sourceId` 只用于同一任务卡的状态投影，不用于控制图执行；
- 预期的计划确认、网络确认和知识库确认 Interrupt 显示为“等待用户”，不显示“上次执行已中断”。

## 10. 原型结论

原型：`prototypes/phase6_research_progress_stream_probe.py`

已验证：

- `stream_mode=["messages", "updates"]` 可以同时观察消息与节点更新；
- `subgraphs=True` 能稳定区分嵌套 Research namespace；
- 服务端可把 Research 更新单向转换为产品事件；
- 当前继承式子图内部节点更新虽然可见，但父图没有单来源 checkpoint，整个子图仍属于父图的一个超级步。

因此“详细实时展示”和“来源级 checkpoint 恢复”是两个不同问题，不能因为前者实现了就宣称后者也实现了。

## 11. 已确认事项

### 11.1 Checkpoint 粒度

本阶段保持当前继承式 checkpointer。接受断连后 Research 子图从较早位置重跑，以及产品时间线出现重复来源事件。它符合此前确认的超级步恢复语义。

### 11.2 阶段 6 与阶段 7 的入库边界

阶段 6 可以完成报告、询问用户并持久化 `knowledge_decision`，但阶段 7 才会实现个人知识库资源仓库、权限隔离和 Index 导入服务。

已确认：

- 阶段 6 的 approve 表示用户已经授权；决定保留在 checkpoint 和结构化结果中；
- 阶段 6 不写全局 `MARKDOWN_DIR`，也不假装已经入库；
- wrapper 明确返回 `import_status=pending` 或 `not_requested`；
- 阶段 7 接入正式导入服务后，approve 分支才执行实际个人知识库导入；
- 阶段 6 验收重点是“拒绝绝不写入”和“授权决定可恢复”，不宣称 RAG 已能检索该报告。

### 11.3 报告与 Main Agent 工作记忆边界

- 完整报告由 `research.report` 产品事件在当前 Thread 中展示；
- 完整报告不会进入 `MainState.messages`；
- wrapper 只返回主题、短摘要、来源数、研究结果和入库状态等精简元数据；
- wrapper 不再额外插入重复的 `SystemMessage`；
- 不创建独立 ResearchArtifact 仓库；
- 不增加 `read_research_result` 工具；
- 用户拒绝入库后，报告只保留为当前 Thread 的历史展示以及 LangGraph 的技术性 checkpoint，不成为可由 Agent 主动读取或 RAG 检索的知识。

## 12. 阶段验收草案

- Research Agent 全程位于聊天区，不打开 Resume 工作区；
- 计划、关键词、URL、抓取、提炼和报告状态均可见；
- 单来源失败不会让整张任务卡失真；
- 刷新后能从产品事件恢复已有任务卡；
- 预期 Interrupt 不显示意外中断提示；
- 报告完成前不会出现知识库确认；
- 用户拒绝后不产生 Markdown、索引或向量写入；
- wrapper 不再谎称资料已经入库；
- 图运行不依赖产品事件；
- ruff、mypy `--strict`、后端精简测试和前端构建通过。
